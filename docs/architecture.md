# Orbit architecture

How Orbit is built and why it behaves the way it does. For what each control does, see the [user guide](user-guide.md). The code map is in the [README](../README.md#architecture).

## Overview

Orbit is a Tauri 2 desktop app. The React frontend renders a snapshot of the engine's state and sends a small set of named commands. The Rust engine does everything else: polling GitHub, scheduling reviews, preparing worktrees, talking to Codex, publishing, and saving state. Polling and review orchestration run in Rust, independent of which view is open. Orbit must remain running; this version does not install a background daemon or GitHub webhook.

Orbit uses the `gh`, `git`, `codex`, and (optionally) `claude` executables installed on your `PATH` rather than bundling a Codex binary. GitHub CLI and Codex manage their own authentication; Orbit does not request or store copies of your tokens.

## Codex app-server protocol

- Codex uses newline-delimited app-server messages over stdio: `initialize` → client `initialized` → `thread/start` → `review/start`; follow-ups use `thread/resume` and `turn/start`. Streaming and final review items are routed by thread and turn IDs.
- The environment setup command runs in the new worktree through Codex's sandboxed `command/exec`, with a five-minute timeout.
- The usage meter reads `account/rateLimits/read` (with `excludeResetCreditDetails`) on connect and every five minutes, and merges each sparse `account/rateLimits/updated` notification into the last read (`src-tauri/src/usage.rs`). It is shown only, never saved, and never holds back a review.
- Security scans (`src-tauri/src/engine/scans.rs`, data handling in `src-tauri/src/scans.rs`) find the Codex Security plugin with `plugin/list`, install it with `plugin/install` only when the user asks (a remote marketplace's plugin by its `remotePluginId`), and find its skill paths with `skills/list` (no `cwds`, so Codex lists those of its own working folder), keeping only skills whose `pluginId` is the plugin's, so no other skill of the same name is ever run. A scan fetches the remote's `HEAD` into a detached worktree under `scan-worktrees/`, starts its own thread there (`approvalPolicy: "never"`, workspace-write sandbox with network off and Orbit's `scan-output/` folder writable), and starts one turn with the request text plus a `{type: "skill"}` input. Orbit starts Codex with `CODEX_SECURITY_SCAN_ROOT` set to `scan-output/`, so the plugin's scans live in Orbit's folder. Progress comes from the plugin's `update_codex_security_scan_progress` tool calls and `CODEX_SECURITY_SCAN_PROGRESS` markers; the scan folder from its start tools' results. On `turn/completed`, Orbit first checks the plugin's completion record: `scan-manifest.json` must be a sealed Codex Security manifest (`sealedAt` set, a finished status) for a plugin scan that `list_codex_security_scans` reports on this copy, at the scanned commit, with every sealed file's SHA-256 unchanged and sealed `findings.json` and `coverage.json` documents naming the same scan. Only then does Orbit import `findings.json` (critical/high/medium/low to P0/P1/P2/P3), copies the kept files to `scans/<id>/`, and deletes `artifacts/` only inside `scan-output/`, and only after a scan the plugin recorded as completed. An ended turn is never taken as proof that the plugin's work stopped. A turn that ended without that record, one that ended while the plugin still lists its scan as running, a failed or interrupted turn, Cancel, and a running scan when Orbit restarts or Codex disconnects all move the scan to `cancelling` (shown as Stopping), with the status and reason to record once it has stopped. `cancelling` keeps the one-scan slot, the scan's worktree and its files, and blocks deletion. Orbit interrupts the turn (reopening the thread with `thread/resume` when a new Codex process no longer has it), then calls the plugin's tools itself with `mcpServer/tool/call` on the scan's thread: `list_codex_security_scans` finds the plugin's scans on the scan's copy (a deep scan's id is not reported until it ends), `cancel_codex_security_scan` stops each running one, since a deep scan's workers outlive an interrupted turn, and a second list confirms none still runs. Only then does the scan end (`cancelled`, or the failed or interrupted status it was stopping for) and lose its worktree; if any step fails it stays `cancelling` with the reason, and Cancel can be tried again. Stops are retried whenever Codex connects.
- Findings come from a second turn on the review's thread: `turn/start` with an `outputSchema` (`src-tauri/src/engine/findings.rs`) asks Codex to restate its report in Orbit's form. Each finding has a title, priority, category, one or more locations, the problem, a failure scenario, evidence, whether it was confirmed, a suggested fix, a done-when check and the reviewer's own notes, plus a confidence. Structured output requires every property, so parts a report may lack are typed string-or-null. `findings::parse` refuses the whole answer if any part is malformed, so a run never keeps a partial list. The answer also says what the reviewer could not check (`notChecked`) and whether it finished (`completed`); `completed: false` fails the run instead of publishing. Claude and Antigravity use the same schema through `--json-schema`. Findings and reviews saved before this form still load, with the new parts empty.
- Publishing (`src-tauri/src/engine/inline.rs`): each finding's short ID number is set when its findings are stored, one past the highest any other review of the pull request used (`findings::next_number`), so it is never reused; the review keeps the blocking priority it was judged with (`blocking_priority`) for the Blocking labels. The review's text ends with the reviewer's report in `<details>` and an `<!-- orbit-data {json} -->` comment holding the whole form (version 1), with `<`, `>` and `&` written as JSON `\u` escapes so the text can't close the comment. To stay under GitHub's limit Orbit drops the data, then the report, then both. `findings::report_count` counts the findings in the reviewer's report (`[P#]` lines for Codex, `### Problem N:` headings Orbit's instructions ask Antigravity for, and the count in Orbit's rendering of Claude's JSON list) for the "may have been left out" note. The `orbit-review`, `orbit-verdict` and `orbit-finding` markers are unchanged, so earlier comments still match.
- Replies (`src-tauri/src/engine/claims.rs`): when a re-review carries the previous round, Orbit reads the trusted comments line by line for `Fixed F2 in <sha>` and `Declined F2: <reason>` (or, in a finding's thread, without the short ID), keeps the latest claim per carried finding in `PreviousRound.claims`, and places a named commit with `git rev-parse --verify` and `merge-base --is-ancestor` against the previous and current heads. The parser only accepts 7 to 40 hex characters, so a commit can't be read as a Git option. Claims go into the round's notes for the reviewer, the published **Author said** column, exports and the hidden data; the reviewer still classifies each finding.
- Reply skill (`.claude/skills/answer-orbit-reviews/SKILL.md`): a Claude Code skill for the author's agent that teaches the reply lines above. `claims_tests::the_reply_skill_teaches_lines_orbit_reads` reads its examples and every reply form it names with the same parser, so the two can't drift apart. Settings imports the file with Vite's `?raw` and offers it to copy; Orbit never writes it into a repository.
- Approvals are routed to the user explicitly (`approvalsReviewer: "user"`), even when a different reviewer is configured globally in Codex. Command and file-change escalation requests are displayed for a person to approve or deny; unknown interactive requests are not automatically granted.
- The compatibility baseline is Codex CLI **0.156.1** and the [official app-server protocol](https://developers.openai.com/codex/app-server). Re-reviews use Codex's `custom` review target, because review mode at 0.156.1 runs with no thread history and no turn-level developer instructions, so the previous round has to go in the target itself (see `src-tauri/src/engine/rounds.rs`).

## Claude Code CLI

A repository can choose Claude as its reviewer (`Provider` in `src-tauri/src/types.rs`). Both reviewers feed the same engine through `ReviewEvent` (`src-tauri/src/engine/events.rs`), so rounds, findings, publishing and the loop do not depend on who reviewed.

- Each turn is one `claude -p` process (`src-tauri/src/claude.rs`, started and read by the plumbing it shares with Antigravity in `src-tauri/src/cli.rs` and `src-tauri/src/engine/cli_review.rs`) with `--output-format stream-json`. The review turn runs `/code-review <effort> <base>...HEAD` under a new `--session-id`; the findings turn resumes that session with `--json-schema` (Orbit's findings schema, the same one Codex gets) and reads `structured_output`. A later round's earlier findings and replies go into the findings turn. Follow-ups resume the same session.
- Every turn passes `--model` and `--effort`, and Orbit checks the model the `init` event reports before saving the confirmation. Claude does not echo effort back.
- Isolation: `--setting-sources ""` and `--strict-mcp-config` switch off the user's settings, hooks, plugins and MCP servers; `--permission-mode dontAsk` declines anything not allowed instead of asking; `--tools` and `--allowedTools` allow only Read, Grep, Glob, Task and a short list of Git and text commands, with Git's `--output`, `--ext-diff` and `--textconv` denied; `--settings` turns Claude's sandbox on with `autoAllowBashIfSandboxed` off, so sandboxed commands still need the allow list, and with `failIfUnavailable`, so Claude refuses to start rather than run commands unsandboxed. That matters because an allowed `git diff` can still run a diff driver the clone configures, pointing at a script the pull request controls. Declined calls (`permission_denials`) are noted in the report, and a findings turn that reports `completed: false` fails instead of looking clean. Like Codex's, the sandbox is not a full read boundary.
- `claude auth status` checks the sign-in on connect. Reviews of repositories that use Codex never start `claude`.

## Antigravity CLI

A repository can also choose Antigravity (`agy`) as its reviewer. Antigravity has no review mode, so Orbit gives it Orbit's own review instructions (`src-tauri/src/review_instructions.rs`).

- Each turn is one headless `agy` process (`src-tauri/src/antigravity.rs`) with `--output-format stream-json --input-format stream-json`. The prompt goes in on standard input, which then closes, so the process ends after one turn. The review turn's prompt is Orbit's instructions plus the change. Orbit computes the change itself with `git diff --no-ext-diff --no-textconv <base>...HEAD`, so no diff driver the clone configures runs. A diff over 200 KB is written whole to `.orbit-change.diff` in the worktree for Antigravity to read in parts. Orbit refuses the review if the pull request already has a file there, and doesn't count the file as a change the reviewer made. The findings turn and follow-ups continue the conversation with `--conversation <id>`. The id comes from the review turn's `init` event. The findings turn uses `--json-schema` with the same schema as Claude's.
- Every turn passes `--model`, `--effort` and `--sandbox`. A process that answers but doesn't exit is killed with the commands it started, and the turn fails. It never passes `--dangerously-skip-permissions`. Orbit stops the turn before saving anything unless `init` reports all three of:
  - the requested model,
  - the expected conversation,
  - a permission mode that asks for approval (`request-review` or `strict`).
    With no one to approve, Antigravity soft-denies what needs approval: shell commands by default. The denials it prints on standard error are noted in the report. A standard-error line saying the sandbox couldn't start kills the process.
- Orbit reads Antigravity's global settings (`~/.gemini/antigravity-cli/settings.json`) but never changes them. Before every check and turn, Orbit refuses to review if the settings would let a pull request reach past the sandbox:
  - allow rules for `unsandboxed`, `read_url`, `execute_url`, `mcp`, `read_file` or `write_file`. Inside the worktree, files need no rule, so file grants only reach outside it.
  - a `toolPermission` other than `request-review` or `strict`,
  - `allowNonWorkspaceAccess`.
    Commands the developer allowed with `command(...)` rules run inside the sandbox, with the worktree writable and no network. Like Codex with `AGENTS.md`, Antigravity reads the repository's own `AGENTS.md` and `.agents/` rules, which the pull request controls.
- `agy models` checks the CLI on connect. It confirms the CLI is installed and signed in, and lists the models Settings offers. Antigravity has no default model in Orbit, so its reviews need a model chosen in Settings.
- Built from Antigravity's published headless documentation and tested against a fake `agy` (`src-tauri/src/agy_fixture.cjs`). It has not yet been run against the real CLI.

## Dev containers

A repository can run its setup and check commands in its dev container instead (`DevContainer` on `Repository`; `src-tauri/src/devcontainer.rs`, driven by `src-tauri/src/engine/checks.rs`). This works for every reviewer, so Claude and Antigravity reviews may have a setup command too.

- During preparation, after the worktree and the previous round, Orbit reads the base commit's `.devcontainer` tree (`git rev-parse <base>:.devcontainer`) and requires a `.devcontainer/devcontainer.json` there. The pull request's own recipe is never used. The image is `orbit-devcontainer:<owner>.<repo>-<first 12 characters of that tree>`, so a changed recipe gets a new image and an unchanged one is reused. Only the `.devcontainer` folder is in the key: a recipe that copies other files into its image is rebuilt only when `.devcontainer` changes.
- A missing image is built with the Dev Container CLI (`devcontainer build --workspace-folder <checkout> --image-name <image>`) from a detached checkout of the base commit under `recipes/<review>`, which is removed afterwards. One image builds at a time (`Engine::building`). Building runs the base branch's recipe on your computer with network access, as the CLI does for you.
- The checks run in a new container: `docker run --detach --rm --label dev.orbit.checks=<review> --security-opt no-new-privileges --pids-limit 4096`, with `--network none` unless the repository's network access is on, and `sleep` as the entry point for at most two hours, so a container Orbit loses track of removes itself. It gets no folders from this computer, no environment, no sign-ins and no Docker socket. Orbit copies the worktree in with `docker cp` to `/workspaces/<repo>`, deletes the copied `.git` file (it points at your clone), and gives the folder to the recipe's `remoteUser` (else `containerUser`) from the image's `devcontainer.metadata` label, else to the image's own user, such as a Dockerfile's `USER`. Orbit reads that user before starting the container, and an image it can't read fails the review. The setup command, then the check command, run as that user with `/bin/sh -c` in that folder, with 15- and 30-minute limits. A failed setup skips the check command. The container is then removed (`docker rm --force`), also when the review is stopped or replaced while its checks run: stopping the `docker` commands on this computer doesn't stop the container or the commands in it, so the removal runs on its own, after any `docker run` Docker already has finishes. At launch Orbit removes any container with its label and any leftover recipe checkout.
- Each step's exit code, time and last 12 KB of output are kept on the review (`Review::checks`) and summarised in its chat. A command that fails is a result, not an error; a recipe that's missing or doesn't build, or Docker failing, fails the review with the reason.
- The results reach the reviewer inside a delimited block with a random tag, marked as data, since the output comes from running the pull request's code (`devcontainer::notes`). Codex gets them in custom review instructions: a first round asks for the same base-branch review it would otherwise run (`rounds::base_review`), followed by the results. Antigravity gets them after the change in its review prompt. Claude's `/code-review` turn runs as before; its findings turn gets the results and read-only tools, and adds failures the change caused.
- The reviewer still works in the worktree on this computer, in its own sandbox, as above. Only the pull request's setup and checks move into the container: putting the reviewer there too would put your sign-ins in a box that runs the pull request's code.
- `docker version` and `devcontainer --version` are checked with the reviewers on connect (`Snapshot::dev_containers`). On Windows the CLI is started through `cmd /C`, since npm installs it as a `.cmd` script.
- Tested against a fake `docker` and `devcontainer` (`src-tauri/src/devcontainer_fixture.cjs`), which keeps containers as folders and runs commands with the host's shell. One test, skipped by default, uses the real tools: `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features real_docker -- --ignored` builds a recipe from `alpine:3.20` and checks the commands run as the recipe's user, in `/workspaces/<repo>`, without `.git` or network, and leave the worktree untouched.

### Model pinning

Every new review pins an explicit model and effort when queued. Orbit validates that pair against the connected account's catalog before enqueueing and preparation. Changing workspace Settings affects future runs only. Model selection uses the catalog's `model` identifier, not its display ID. How empty settings are resolved is described in the [user guide](user-guide.md#settings-and-when-changes-take-effect).

Orbit sends the pinned model, matching `review_model`, and reasoning effort on thread creation. It requires Codex's returned model and effort to match exactly and persists the confirmation before `review/start`. Every follow-up resumes with its pinned pair, verifies and saves the confirmation, and passes the same model and effort on `turn/start`. Missing/null or mismatched responses stop execution. Threads created during a stopped or rejected preparation are archived; if archiving fails, Orbit tries to unsubscribe and records the thread ID in the chat. Orbit does not request provider fallback or modify your Codex configuration.

For older chats missing a recorded selection, Orbit unsubscribes its idle thread before the first legacy resume so Codex can apply overrides (0.156.1 applies changed overrides to an idle loaded thread only after its subscribers detach). If another subscriber prevents that change, response verification stops the turn.

## GitHub

- Each sync lists each connected repository's open PRs with one request and fetches an individual PR only when it is new or has changed. A repository that fails to sync keeps its last-known PRs and shows an error while the others continue, and autopilot only acts on repositories that synced successfully in the current session.
- Before publication, Orbit checks that the PR is still open and both SHAs still match. GitHub does not offer an atomic compare-and-comment endpoint, so a commit can still arrive in the small interval between that check and the POST; comments always identify the exact reviewed SHAs.
- A stable marker in each comment and review reconciles ambiguous retries after a timeout or restart. A local instance lock prevents two Orbit processes from using the same state directory concurrently. This is local deduplication, not coordination across multiple computers.

## Isolation and its limits

Orbit fetches GitHub's PR head ref and the captured base commit into the configured clone, verifies the head SHA, and creates a detached worktree under its app-data directory. This changes Git metadata but does not check out or edit the original working tree. Git hooks are disabled for these operations. Temporary `refs/orbit/*` refs are deleted from your clone as soon as the worktree exists.

Each review gets its own Codex thread and working directory. Setup and agent commands use the Codex **workspace-write** sandbox, with network access disabled unless configured for that repository.

This is a **worktree plus the Codex OS sandbox**, not a VM or a Docker/devcontainer environment, unless the repository runs its setup and checks in its [dev container](#dev-containers). Then the pull request's setup and checks run in a container, but the reviewer itself still works in the worktree. Otherwise it uses host-installed tools, the repository's manifests/lockfiles, and the user-configured setup command. Worktrees do not copy untracked dependencies or secrets from the original clone. Codex's local configuration, provider access, sandbox support, and managed policies still apply; this app does not claim to hide all host files or all inherited integrations from Codex, such as hooks and skills. Only configure repositories and setup commands you intend to run.

Extra tools (`src-tauri/src/extras.rs`, `src-tauri/src/engine/extras.rs`): the review's `thread/start`, and the `thread/resume` before a follow-up or the findings turn, send `extras::off` in their `config`: each MCP server that `config/read` (with the thread's `cwd`) reports switched off by name, and the features in `extras::FEATURES_OFF` (plugins, apps, browser use, computer use, tool suggestions, memories, image generation) off. The thread/start `config` is deep-merged onto the user's Codex config, so an empty `mcp_servers` wouldn't remove servers; each needs `enabled: false`. A cold `thread/resume` doesn't keep the thread's earlier overrides, so every resume sends them again. Before `review/start` or `turn/start`, `mcpServerStatus/list` for the thread must show every server `disabled`; otherwise, or if Codex can't list them, the review doesn't start (its new thread is archived) or the turn isn't sent. Codex's review mode runs on the thread's config, so its reviewer gets only Codex's standard tools. A scan (`extras::off_except_plugin`) keeps plugins on but switches off each other installed plugin (from `config/read` and `plugin/list`) and, inside each, every server name Codex lists without a thread but `codex-security`: Codex ignores a thread's `enabled` for a plugin installed from the user's account, but not its servers. The scan's thread must then show only `codex-security` on. Checked against codex-cli 0.162.1.

> [!WARNING]
> Because the agent can read files outside its worktree, a pull request can plant instructions in its diff that try to get local secrets quoted in the report. That is why automatic review and publication are restricted to repository insiders: pull requests from a branch in the repository itself, by an owner, organization member, collaborator, or trusted account. The setup command can also execute code from the pull request, such as package install scripts, so prefer options like `--ignore-scripts`. With network access enabled for a repository, both setup and the agent can reach the network.

A report is never published automatically when it contains text matching a well-known credential format, and publishing one manually requires an explicit confirmation. The scan is a best-effort backstop, not a guarantee: secrets without a recognizable format are not detected.

## Persistence and recovery

- State is atomically replaced in `state.json` under Tauri's app-data directory (typically `~/.local/share/dev.orbit.review` on Linux). Invalid state is left untouched.
- Active runs become visibly interrupted after restart instead of being silently retried.
- A state-write failure turns Autopilot off; after resolving it, re-enable Autopilot to resume automatic reviews.
- Threads and worktrees are retained for follow-ups. Orbit removes a review's worktree automatically once its pull request is no longer open in a connected repository (merged, closed, or the repository was disconnected), and when a review fails or is stopped before it starts; the chat stays readable, but follow-ups then need a new review.
- Manual worktree removal checks registered ownership and eligibility under the Git lock, persists cleanup intent before touching files, and recovers pending removals after restart. Interrupted automatic cleanup rechecks PR closure on restart, independently of initial inbox sync.

## Buddy

Bit's notes are written by the engine, not the UI, so they cover what happened while the window was closed. `src-tauri/src/buddy.rs` holds the settings (`Buddy`, checked in `Settings::validate`), the feed, the mood, the fixes and their rules, the quick answers, and the note templates for each tone.

- After each change, `Engine::flush` runs `attention::announce` (the once-only Needs you notices) and then `buddy::observe` with the items that just opened. `observe` compares each loop's `review_loop::state` with what Bit last saw (`SeenLoop`: rounds started and finished, stopped, extra rounds) and writes one note per change, plus one per new Needs you item. The first look at a workspace, and a loop it meets with more than one round behind it, are only recorded, so an upgrade or a PR returning to the inbox doesn't retell old rounds.
- The feed (`Snapshot.buddy_feed`) is saved in `state.json`, keeps the last 50 notes, and numbers them so the UI has stable keys. Loops are recorded even while the buddy is off, so turning it on doesn't replay them.
- The mood is worked out in `attention::shown` from the same snapshot every client sees, and is never saved.
- Fixes: `attention::items` gives each item the `Fix` that resolves it, if one of Orbit's own controls does (`ContinueLoop`, `ReviewAgain`, `Publish`, `SyncNow`, `TurnOnAutopilot`, `CheckConnections`); approvals have none. A `Disconnected` item (`connection:<key>`) opens for each of `guide::connections` other than GitHub (whose problems are the sync items') that has an error, isn't ready and is used by a connected repository: Codex, Claude, Antigravity, or the dev container tools. Its `CheckConnections` fix runs `Engine::check_connections` (`engine/setup.rs`): the reviewers' checks, `connect`, then a sync, as Settings' Reconnect does; it succeeds once the item has closed. Like `TurnOnAutopilot`, it has no rule and always waits for a tap. `Publish` is only offered for a current report that automatic publication wouldn't hold, so never for a credential-flagged one or one from an untrusted source. The UI shows the fix as a button on a note or answer line whose `key` names an open item, and runs it with `use_fix` (`engine/fixes.rs`), which looks the item up again by key, uses the control as the app's own button does, and writes a `Fixed` note.
- Do it: in `Engine::flush`, an item that just opened whose fix's rule is `do_it` (`buddy::will_fix`, only while Bit is on) gets a `Fixing` note from `observe` instead of a `NeedsYou` one, skips the desktop notification, and joins `Engine::fixing`. The next tick's `do_fixes` runs each in its own task and writes `Fixed`, or, when the fix fails while its item is still open, a `NeedsYou` note with the item's key and a notification. A queued fix runs only while it is still Bit's (`still_mine`: the item is open about the same report with the same fix, and `will_fix` still agrees), checked under the same state lock as the change (`continue_loop_if`, `enqueue_if`); one whose item closed meanwhile is dropped. Bit publishes as `publish::By::Bit`, which repeats that check and applies automatic publication's trust and credential holds to the fresh PR before every write, independent of the publication switch, for buttons and Do it alike. `TurnOnAutopilot` changes settings, so its rule is always `ask_first`. Sync now waits for a sync already running (`poll_lock`), checks again, then syncs (`poll_holding`), and counts as done only once the item has closed. `attention::announce` judges a report being published as still ready, so a publication that fails doesn't make its item new again and Bit tries a Do it fix only once.
- Quick answers: `ask_buddy` writes an `Answer` note with the question and one `NoteLine` per thing it lists, worked out from the snapshot (`buddy::ask`), so every window sees the same conversation. No model is involved.
- Setup help (`guide.rs`): **Help me set up** (`Question::Setup`) first runs `Engine::look_up` for each connected repository's copy, and lists your GitHub repositories only while none is connected. `guide::setup` turns the snapshot and lookups into lines and proposals, the same `Proposal`s typed answers offer, each checked through `ask::set_up_proposal` or `ask::autopilot_proposal` as an answer's would be: a `CheckConnections` proposal when a connection is off, up to 3 `connect` proposals when nothing is connected, then per repository a setup command from `setup::suggest` (the first file of `setup::SETUP_COMMANDS` the copy has, with network access) when it has none and its reviewer can run one, and automatic reviews when they're off, then global autopilot. `Guide::to_do` counts what's left for the answer's opening line. When a repository is added, from `save_repository` or a `connect` proposal, `Engine::note_connected` writes a `Connected` note with `guide::connected`'s steps for just that repository, if Bit is on. `clone_facts` passes the suggestion to typed questions too, as the copy's `suggestedSetup`.
- Typed questions: `ask_buddy_anything` (`engine/ask.rs`) writes a pending `Answer` note (`buddy::asked`), then starts a Codex thread of its own with the Codex model and effort from Settings, `sandbox: read-only`, `approvalPolicy: never` and an empty `bit` folder in Orbit's data folder as its working directory. Its `config` (`ask::thread_config`) turns off web search, the extras (`extras::off`, above) and the standard tools in `ask::TOOLS_OFF` (commands, images, sub-agents, goals, hooks), for this thread only. Before the turn starts, `mcpServerStatus/list` for the thread must show every server `disabled`; otherwise, or if Codex can't list them, the thread is archived and the question isn't asked. One question runs at a time (`Engine::asking`). `ask::instructions` tells Codex who it is, the tone and personality, and that the state is data; `ask::prompt` sends the question with `ask::briefing`, a summary of the snapshot that leaves out trusted accounts, clone paths and PR bodies, hides a setup or check command the credential scan flags, and clips titles. Before the prompt is built, `Engine::look_up` (`engine/setup.rs`) adds `ask::Lookups`: each connected repository's copy as `setup::clone_facts` reads it (telltale files from `setup::TELLTALE_FILES`, and `package.json` script names and package manager only when short and plain), and one page of `github::recent_repositories` minus the connected ones, with a 10-second limit; a look that fails puts its error in the summary instead. The names offered to connect are kept on the question (`Asking.connectable`) so the answer is checked against them. The turn's `outputSchema` (`ask::output_schema`) asks for `{answer, proposals, memory}`. `Engine::event` routes the thread's notifications to `answer_event` before scans and reviews; `turn/completed`, a 3-minute timeout, or a Codex disconnect ends the question, and the thread is archived (interrupted first if unfinished). `ask::answer` refuses an answer the credential scan flags, clips it, and keeps only proposals for an allowed action that apply now (at most 3): a known PR whose loop can be stopped or continued, nothing running for Review again, `attention::may_publish` for Publish, for Change settings a change to one of `ask::SETTINGS` (never trusted accounts or repository settings) that parses as a `SettingsPatch`, passes `Settings::validate` and changes something, and for Set up repository a `setup::RepositoryPatch` built by `setup::patch` from `setup::REPO_SETTINGS` (one-line commands of up to 500 characters that the credential scan doesn't flag and `setup::denied` allows, the round and approval limits Repositories offers) for a connected repository it changes, or for one the summary offered to connect (`connect: true`), whose result passes `Repository::check`. A pending note found at startup says Orbit closed before it could answer (`buddy::recover`).
- Bit's memory: `Feed.memory` (`buddy::Memory`, saved in `state.json` with the feed) holds general lines and lines per repository. The briefing includes it with its limits, and `ask::instructions` says what is worth keeping. An answer's `memory: {forget, remember}` lists lines with a repository or null; `ask::memory_change` turns each into one line of at most 200 characters with no control characters, drops a remembered line the credential scan flags, and keeps a repository only if it is connected (or, for forgetting, already in memory), at most 10 changes per answer. `buddy::answered` applies them only while the question is still pending (`change_memory`): forgets first, so a full place can make room, skips a line already kept (ignoring case), and refuses one beyond `MEMORY_GENERAL` (20) or `MEMORY_PER_REPO` (10) as `full`. The changes made are recorded on the answer note. `forget_memory {repo, line}` and `clear_memory` let you remove lines from Settings; each advances `Engine::memory_generation`, and an answer whose question was asked before that drops its memory changes (its text and buttons still show), so it can't bring back what you forgot.
- Answer buttons: `use_proposal` runs a proposal only when tapped, and once: it claims the button in `Engine::using` under the state lock before any await, refuses a second tap while the claim lasts, marks it `done` before the claim ends, and drops the claim on failure so it can be tapped again. It goes through the same engine paths as the app's controls, which check again: `continue_loop`, `stop_loop`, `enqueue`, `publish_by(By::Bit)` (the fresh trust and credential checks before every write), a sync under `poll_lock`, `update_settings`, refusing a patch that touches trusted accounts, and `Engine::set_up_repository` for Set up repository: a connected repository gets the patch through `commit_settings`; a button without `connect` fails for one disconnected since; otherwise, under `cloning`, Orbit runs `gh repo clone` into `downloads/<owner>/<name>` (`setup::download_folder`, cleared first) and moves the finished copy to `clones/<owner>/<name>` in its data folder (`setup::clone_folder`) unless that folder exists, so a download cut short is never connected, then checks the copy's origin (`validate_checkout`) and, under the state lock, connects it with `Repository::new`'s defaults, keeping the copy up to date, plus the patch, or gives the patch to the repository if it was connected meanwhile, and starts a sync.
- The colour, hat, tone, rule, fix, question and action lists, and the memory limits, live in `buddy.rs` and the app (`src/Bit.tsx`, `src/types.ts`); `test-fixtures/buddy-options.json` holds them once, and tests on both sides check against it. An older state file without buddy settings gets the defaults, and a value a newer Orbit saved that this one doesn't know falls back to the default.

## Concurrency and locking

The engine's locks, what each protects, and the order to take them in are documented on the `Engine` struct in [`src-tauri/src/engine/mod.rs`](../src-tauri/src/engine/mod.rs). In short: one connect, sync, publication, and worktree removal at a time; Git commands against your clones are serialized; and `std` mutexes are never held across an `.await`.

Narrow updates preserve unrelated settings. Global settings and repository operations are ordered independently, so slow checkout validation cannot delay turning Autopilot off. Filesystem validation runs off the async workers with a bounded wait.

## Process lifecycle

On exit, Orbit closes the app-server's stdin and terminates it. Unix process-group termination also cleans up its descendants. Windows uses child-process termination; Windows packaging and descendant cleanup need platform validation.

## Frontend

- The frontend has no generic shell/filesystem/RPC endpoint. Native commands are narrowly scoped (see the allowlist in `src-tauri/src/lib.rs`); CSP restricts network access, raw Markdown HTML is not executed, and remote Markdown images are not fetched.
- Report export is generated and written in Rust; the frontend supplies only a review ID.
- Browser access (`src-tauri/src/remote.rs`, `src/remote.ts`, `src/RemoteAccess.tsx`) is off until **Settings → Use Orbit from other devices** turns it on; `remote.json` in Orbit's data folder keeps that choice and the port. It serves the same frontend and the same command allowlist on `127.0.0.1` only, for `tailscale serve` to publish. `remote::DESKTOP_ONLY` lists what a browser cannot run: `open_github`, and the access controls themselves, so a browser can't widen or keep its own access. Every `/api` call needs the access token from `remote-token`. The token travels in the link's fragment and an `Authorization` header, never a URL or cookie. **Make a new link** replaces the token and restarts the server, which ends every open event stream. Holding the link is as powerful as using the desktop window, including repository setup commands, so share it only with your own devices.
- The UI uses Astryx 0.6.3 with its neutral theme. Astryx core, theme, CLI, and the StyleX peer are pinned; the compiled theme is imported after the core reset and component CSS. The UI is dark-only, uses local system fonts, and makes no font or asset requests to external hosts.
- Settings, repositories, review loops, and chat load on demand. Pages use Astryx shell, layout, controls, dialogs, chat, and Markdown; only the diff's line grid, the Live page's activity chart, and Bit's picture remain custom (`DiffLines` in `src/Files.tsx`, `ActivityChart` in `src/Live.tsx`, and `src/Bit.tsx` explain why). `src/styles.css` contains viewport framing, system-font tokens, compact chat docking, diff styling, the chart's marks and motion, and Bit's strokes. Bit is an SVG whose colours are all theme tokens; it animates only while busy and holds still when the system asks for reduced motion. The Live and Findings pages are derived entirely from the snapshot; they add no backend state. `src/findingIndex.ts` follows each finding by its stable ID (`{reviewId}-{index}`) through later rounds' `priorFindings` to work out its current status, and adds finished scans' findings (IDs `{scanId}:{findingId}`) as open, with no PR. The backend, command allowlist, store behavior, and browser demo adapter are independent of the component layer.
- Astryx component guidance is generated in [`AGENTS.md`](../AGENTS.md). Before changing UI, use `npx astryx component <Name>` for the installed API.

## Design notes

The supplied architecture document was used as a recommendation. This implementation corrects the protocol lifecycle and event names, uses existing installed CLIs instead of bundling a Codex binary, and uses Astryx with its neutral theme.

Not included in this version: macOS/Windows installers, signing, auto-update distribution, and container-backed environments. Native prerequisites vary by OS.

## Verification

Controllable app-server fixtures verify model migration, reconnect recovery, immutable queued selections, exact response checks, persistence before inference, and legacy chat pinning without live inference or GitHub publication. A fake `gh` (Unix only) drives the GitHub paths. Component tests cover explicit Settings choices, the legacy selector, Astryx dialog lifecycle and shortcut isolation, guarded composer submission, and Markdown safety (images dropped, links rendered as text, no HTML execution or autolinking). Tests also exercise queue limits, cancellation, publication retry/link rendering, stale file responses, navigation shortcuts, autosave failures/serialization, status/send eligibility, repository validation, worktree cleanup contention/containment/recovery, Markdown export, streamed reports, RPC failures, persistence, and the instance lock. Rust filesystem tests use disposable repositories and state.

Native Linux GTK Save As checks on a virtual display cover successful export, cancellation, overwrite confirmation, and extensionless filename confirmation using disposable review data. Browser checks cover search, review/chat actions, publication previews, changed files, repository configuration, and responsive navigation. Real authentication and model discovery were verified; live inference and posting are not part of the read-only diagnostic (`npm run diagnose`), which uses a temporary state directory.
