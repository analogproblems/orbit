# Orbit architecture

How Orbit is built and why it behaves the way it does. For what each control does, see the [user guide](user-guide.md). Where each part lives is in the [code map](#code-map).

## Overview

Orbit is a Tauri 2 desktop app. The React frontend renders a snapshot of the engine's state and sends a small set of named commands. The Rust engine does everything else: polling GitHub, scheduling reviews, preparing worktrees, talking to Codex, publishing, and saving state. Polling and review orchestration run in Rust, independent of which view is open. Orbit must remain running; this version does not install a background daemon or GitHub webhook.

Orbit uses the `gh`, `git`, `codex`, and (optionally) `claude`, `agy`, `docker` and `devcontainer` executables installed on your `PATH` rather than bundling a Codex binary. GitHub CLI and Codex manage their own authentication; Orbit does not request or store copies of your tokens.

## Codex app-server protocol

- Codex uses newline-delimited app-server messages over stdio: `initialize` → client `initialized` → `thread/start` → `review/start`; follow-ups use `thread/resume` and `turn/start`. Streaming and final review items are routed by thread and turn IDs.
- The environment setup command runs in the new worktree through Codex's sandboxed `command/exec`, with a five-minute timeout.
- The usage meter reads `account/rateLimits/read` (with `excludeResetCreditDetails`) on connect and every five minutes, and merges each sparse `account/rateLimits/updated` notification into the last read (`src-tauri/src/usage.rs`). It is shown only, never saved, and never holds back a review.
- Security scans (`src-tauri/src/engine/scans.rs`, data handling in `src-tauri/src/scans.rs`) find the Codex Security plugin with `plugin/list`, install it with `plugin/install` only when the user asks (a remote marketplace's plugin by its `remotePluginId`), and find its skill paths with `skills/list` (no `cwds`, so Codex lists those of its own working folder), keeping only skills whose `pluginId` is the plugin's, so no other skill of the same name is ever run. A scan fetches the remote's `HEAD` into a detached worktree under `scan-worktrees/`, starts its own thread there (`approvalPolicy: "never"`, workspace-write sandbox with network off and Orbit's `scan-output/` folder writable), and starts one turn with the request text plus a `{type: "skill"}` input. Orbit starts Codex with `CODEX_SECURITY_SCAN_ROOT` set to `scan-output/`, so the plugin's scans live in Orbit's folder. Progress comes from the plugin's `update_codex_security_scan_progress` tool calls and `CODEX_SECURITY_SCAN_PROGRESS` markers; the scan folder from its start tools' results. On `turn/completed`, Orbit first checks the plugin's completion record: `scan-manifest.json` must be a sealed Codex Security manifest (`sealedAt` set, a finished status) for a plugin scan that `list_codex_security_scans` reports on this copy, at the scanned commit, with every sealed file's SHA-256 unchanged and sealed `findings.json` and `coverage.json` documents naming the same scan. Only then does Orbit import `findings.json` (critical/high/medium/low to P0/P1/P2/P3), copies the kept files to `scans/<id>/`, and deletes `artifacts/` only inside `scan-output/`, and only after a scan the plugin recorded as completed. An ended turn is never taken as proof that the plugin's work stopped. A turn that ended without that record, one that ended while the plugin still lists its scan as running, a failed or interrupted turn, Cancel, and a running scan when Orbit restarts or Codex disconnects all move the scan to `cancelling` (shown as Stopping), with the status and reason to record once it has stopped. `cancelling` keeps the one-scan slot, the scan's worktree and its files, and blocks deletion. Orbit interrupts the turn (reopening the thread with `thread/resume` when a new Codex process no longer has it), then calls the plugin's tools itself with `mcpServer/tool/call` on the scan's thread: `list_codex_security_scans` finds the plugin's scans on the scan's copy (a deep scan's id is not reported until it ends), `cancel_codex_security_scan` stops each running one, since a deep scan's workers outlive an interrupted turn, and a second list confirms none still runs. Only then does the scan end (`cancelled`, or the failed or interrupted status it was stopping for) and lose its worktree; if any step fails it stays `cancelling` with the reason, and Cancel can be tried again. Stops are retried whenever Codex connects.
- Findings come from a second turn on the review's thread: `turn/start` with an `outputSchema` (`src-tauri/src/engine/findings.rs`) asks Codex to restate its report in Orbit's form. Each finding has a title, priority, category, one or more locations, the problem, a failure scenario, evidence, whether it was confirmed, a suggested fix, a done-when check and the reviewer's own notes, plus a confidence. Structured output requires every property, so parts a report may lack are typed string-or-null. `findings::parse` refuses the whole answer if any part is malformed, so a run never keeps a partial list. The answer also says what the reviewer could not check (`notChecked`) and whether it finished (`completed`); `completed: false` fails the run instead of publishing. Claude and Antigravity use the same schema through `--json-schema`. Findings and reviews saved before this form still load, with the new parts empty.
- Publishing (`src-tauri/src/engine/inline.rs`): each finding's short ID number is set when its findings are stored, one past the highest any other review of the pull request used (`findings::next_number`), so it is never reused; the review keeps the blocking priority it was judged with (`blocking_priority`) for the Blocking labels. The review's text ends with the reviewer's report in `<details>` and an `<!-- orbit-data {json} -->` comment holding the whole form (version 1), with `<`, `>` and `&` written as JSON `\u` escapes so the text can't close the comment. To stay under GitHub's limit Orbit drops the data, then the report, then both. `findings::report_count` counts the findings in the reviewer's report (`[P#]` lines for Codex, `### Problem N:` headings Orbit's instructions ask Antigravity for, and the count in Orbit's rendering of Claude's JSON list) for the "may have been left out" note. The `orbit-review`, `orbit-verdict` and `orbit-finding` markers are unchanged, so earlier comments still match.
- Replies (`src-tauri/src/engine/claims.rs`): when a re-review carries the previous round, Orbit reads the trusted comments line by line for `Fixed F2 in <sha>` and `Declined F2: <reason>` (or, in a finding's thread, without the short ID), keeps the latest claim per carried finding in `PreviousRound.claims`, and places a named commit with `git rev-parse --verify` and `merge-base --is-ancestor` against the previous and current heads. The parser only accepts 7 to 40 hex characters, so a commit can't be read as a Git option. Claims go into the round's notes for the reviewer, the published **Author said** column, exports and the hidden data; the reviewer still classifies each finding. The same file reads answers to Orbit's CI comments and issues (`ci_lines`: `Taking I2`, `Fixed I2 in <sha>`, `Declined I2: <reason>`, `Need a person on I2: <question>`), which name `I` items and never count as review replies.
- Reply skill (`.claude/skills/answer-orbit-reviews/SKILL.md`): a Claude Code skill for the author's agent that teaches the reply lines above. `claims_tests::the_reply_skill_teaches_lines_orbit_reads` reads its examples and every reply form it names with the same parser, so the two can't drift apart. Settings imports the file with Vite's `?raw` and offers it to copy; Orbit never writes it into a repository.
- Approvals are routed to the user explicitly (`approvalsReviewer: "user"`), even when a different reviewer is configured globally in Codex. Command and file-change escalation requests are displayed for a person to approve or deny; unknown interactive requests are not automatically granted.
- The compatibility baseline is Codex CLI **0.156.1** and the [official app-server protocol](https://developers.openai.com/codex/app-server). Re-reviews use Codex's `custom` review target, because review mode at 0.156.1 runs with no thread history and no turn-level developer instructions, so the previous round has to go in the target itself (see `src-tauri/src/engine/rounds.rs`).
- When the app-server stops, `rpc::Client` keeps the last line it wrote to its error output (`last_error`, shortened, and never a line that looks like a credential), and "Codex disconnected" in Settings says it.

## Claude Code CLI

A repository can choose Claude as its reviewer (`Provider` in `src-tauri/src/types.rs`). Both reviewers feed the same engine through `ReviewEvent` (`src-tauri/src/engine/events.rs`), so rounds, findings, publishing and the loop do not depend on who reviewed.

- Each turn is one `claude -p` process (`src-tauri/src/claude.rs`, started and read by the plumbing it shares with Antigravity in `src-tauri/src/cli.rs` and `src-tauri/src/engine/cli_review.rs`) with `--output-format stream-json`. The review turn runs `/code-review <effort> <base>...HEAD` under a new `--session-id`; the findings turn resumes that session with `--json-schema` (Orbit's findings schema, the same one Codex gets) and reads `structured_output`. A later round's earlier findings and replies go into the findings turn. Follow-ups resume the same session. A turn still running after 60 minutes (`claude::TURN_LIMIT`, the same as Antigravity's `--print-timeout`) is stopped with the commands it started, and fails; the limit is checked in the loop reading its output, so a command still holding that output open can't keep the turn going. When a process exits, `cli::exit` sees it with `waitid(WNOWAIT)` and kills its process group before reaping it, while the group's number can't yet be reused; output still open `EXIT_GRACE` after the exit (held by something that left the group) fails the turn.
- Every turn passes `--model` and `--effort`, and Orbit checks the model the `init` event reports before saving the confirmation. Claude does not echo effort back.
- Isolation: `--setting-sources ""` and `--strict-mcp-config` switch off the user's settings, hooks, plugins and MCP servers; `--permission-mode dontAsk` declines anything not allowed instead of asking; `--tools` and `--allowedTools` allow only Read, Grep, Glob, Task and a short list of Git and text commands, with Git's `--output`, `--ext-diff` and `--textconv` denied; `--settings` turns Claude's sandbox on with `autoAllowBashIfSandboxed` off, so sandboxed commands still need the allow list, and with `failIfUnavailable`, so Claude refuses to start rather than run commands unsandboxed. That matters because an allowed `git diff` can still run a diff driver the clone configures, pointing at a script the pull request controls. Declined calls (`permission_denials`) are noted in the report, and a findings turn that reports `completed: false` fails instead of looking clean. Like Codex's, the sandbox is not a full read boundary.
- `claude auth status` checks the sign-in on connect. Reviews of repositories that use Codex never start `claude`.

## Antigravity CLI

A repository can also choose Antigravity (`agy`) as its reviewer. Antigravity has no review mode, so Orbit gives it Orbit's own review instructions (`src-tauri/src/review_instructions.rs`).

- Each turn is one headless `agy` process (`src-tauri/src/antigravity.rs`) with `--output-format stream-json --input-format stream-json`. The prompt goes in on standard input, which then closes, so the process ends after one turn. The review turn's prompt is Orbit's instructions plus the change. Orbit computes the change itself with `git --attr-source=<base> diff --no-ext-diff --no-textconv <base>...HEAD`, so no diff driver the clone configures runs, and the pull request's own `.gitattributes` can't mark a file binary to hide it (Git before 2.40 has no `--attr-source`, so there every file is shown as text with `--text`). A diff over 200 KB is written whole to `.orbit-change.diff` in the worktree for Antigravity to read in parts. Orbit refuses the review if the pull request already has a file there, and doesn't count the file as a change the reviewer made. The findings turn and follow-ups continue the conversation with `--conversation <id>`. The id comes from the review turn's `init` event. The findings turn uses `--json-schema` with the same schema as Claude's.
- Every turn passes `--model`, `--effort` and `--sandbox`. A process that answers but doesn't exit is killed with the commands it started, and the turn fails. It never passes `--dangerously-skip-permissions`. Orbit stops the turn before saving anything unless `init` reports all three of:
  - the requested model,
  - the expected conversation,
  - a permission mode that asks for approval (`request-review` or `strict`).
    With no one to approve, Antigravity soft-denies what needs approval: shell commands by default. The denials it prints on standard error are noted in the report. A standard-error line saying the sandbox couldn't start kills the process.
- Orbit reads Antigravity's global settings (`~/.gemini/antigravity-cli/settings.json`) but never changes them. Before every check and turn, Orbit refuses to review if the settings would let a pull request reach past the sandbox:
  - allow rules for `unsandboxed`, `read_url`, `execute_url`, `mcp`, `read_file` or `write_file`. Inside the worktree, files need no rule, so file grants only reach outside it.
  - a `toolPermission` other than `request-review` or `strict`,
  - `allowNonWorkspaceAccess`.
    Commands the developer allowed with `command(...)` rules run inside the sandbox, with the worktree writable and no network. Like Codex with `AGENTS.md`, Antigravity reads the repository's own `AGENTS.md` and `.agents/` rules, which the pull request controls.
- `agy models` checks the CLI on connect. It confirms the CLI is installed and signed in, and lists the models Settings offers. Antigravity has no default model in Orbit, so its reviews need a model chosen in Settings.
- Built from Antigravity's published headless documentation and tested against a fake `agy` (`src-tauri/src/agy_fixture.cjs`). It has not yet been run against the real CLI.

## Dev containers

A repository can run its setup and check commands in its dev container instead (`DevContainer` on `Repository`; `src-tauri/src/devcontainer.rs`, driven by `src-tauri/src/engine/checks.rs`). This works for every reviewer, so Claude and Antigravity reviews may have a setup command too.

- During preparation, after the worktree and the previous round, Orbit reads the base commit's `.devcontainer` tree (`git rev-parse <base>:.devcontainer`) and requires a `.devcontainer/devcontainer.json` there. The pull request's own recipe is never used. The image is `orbit-devcontainer:<owner>.<repo>-<first 12 characters of that tree>`, so a changed recipe gets a new image and an unchanged one is reused. Only the `.devcontainer` folder is in the key: a recipe that copies other files into its image is rebuilt only when `.devcontainer` changes.
- A missing image is built with the Dev Container CLI (`devcontainer build --workspace-folder <checkout> --image-name <image>`) from a detached checkout of the base commit under `recipes/<review>`, which is removed afterwards. One image builds at a time (`Engine::building`). Building runs the base branch's recipe on your computer with network access, as the CLI does for you.
- The checks run in a new container: `docker run --detach --rm --label dev.orbit.checks=<review> --security-opt no-new-privileges --pids-limit 4096 --init`, with `--network none` unless the repository's network access is on, and `sleep` as the entry point for at most two hours, so a container Orbit loses track of removes itself. Docker's init runs `sleep` and reaps whatever the commands leave behind, so dead processes can't fill the process limit. It gets no folders from this computer, no environment, no sign-ins and no Docker socket. Orbit copies the worktree in with `docker cp` to `/workspaces/<repo>`, deletes the copied `.git` file (it points at your clone), and gives the folder to the recipe's `remoteUser` (else `containerUser`) from the image's `devcontainer.metadata` label, else to the image's own user, such as a Dockerfile's `USER`. Orbit reads that user before starting the container, and an image it can't read fails the review. The setup command, then the check command, run as that user with `/bin/sh -c` in that folder, with 15- and 30-minute limits. A failed setup skips the check command. The container is then removed (`docker rm --force`), also when the review is stopped or replaced while its checks run: stopping the `docker` commands on this computer doesn't stop the container or the commands in it, so the removal runs on its own, after any `docker run` Docker already has finishes. At launch Orbit removes any container with its label and any leftover recipe checkout, apart from those of reviews that have already started.
- Each step's exit code, time and last 12 KB of output are kept on the review (`Review::checks`) and summarised in its chat. A command that fails is a result, not an error; a recipe that's missing or doesn't build, or Docker failing, fails the review with the reason.
- The results reach the reviewer inside a delimited block with a random tag, marked as data, since the output comes from running the pull request's code (`devcontainer::notes`). Codex gets them in custom review instructions: a first round asks for the same base-branch review it would otherwise run (`rounds::base_review`), followed by the results. Antigravity gets them after the change in its review prompt. Claude's `/code-review` turn runs as before; its findings turn gets the results and read-only tools, and adds failures the change caused.
- The reviewer still works in the worktree on this computer, in its own sandbox, as above. Putting the reviewer itself in the container would mean copying your sign-ins into a box that runs the pull request's code, so instead the reviewer can reach into it:
- With `DevContainer::reviewer_tool` on, the container is kept for the review (`devcontainer::open` → `Opened`, held in `Engine::boxes` as a `checks::ReviewBox`) instead of being removed after the checks; the setup and check commands become optional. The reviewer gets an MCP server, `orbit_box` (`src-tauri/src/boxtool.rs`), whose one tool, `run`, runs `docker exec --user <user> --workdir /workspaces/<repo> <container> /bin/sh -c <command>` (`devcontainer::exec`) for up to 10 minutes, or up to 30 with `timeout_seconds`, and returns the outcome and the last 12 KB of output. Stopping the `docker exec` client leaves the command running in the container, so when any command there runs out of time (the reviewer's, or a kept container's setup and checks) `devcontainer::exec` also runs `devcontainer::STOP_ALL` as root with the shell: `kill -STOP -1` to pause every process but PID 1 (Docker's init), then `kill -KILL` for each one in `/proc` but the `sleep` that keeps the container alive (the init's oldest child: processes left behind become its children too, but later), which it then resumes; up to ten seconds of this until nothing but zombies is left, then `stopped`. It uses only shell built-ins, so it works without `kill` or `ps` in the image and without a new process; a real-Docker test fills the container's 4096-process limit and still stops it. When it doesn't print `stopped` (the exec couldn't start, or a process won't die), Orbit removes the container with `docker rm --force`, which needs nothing inside it; the step's output says so, the reviewer's tool answers with an error that the box is gone for the rest of the review, and a kept container's setup or checks that end this way aren't kept for the reviewer (`Opened::removed`). The server is Orbit's own program started with `--orbit-box-tool <spec JSON>` (`boxtool::serve_if_asked`, first thing in `main`); the CLI starts it outside its own sandbox, which is the point. The reviewer's sign-in never enters the container.
  - Codex: `thread/start` adds `mcp_servers.orbit_box` with `default_tools_approval_mode = "approve"` (review mode runs with approvals off, and an unapproved tool call fails there) and `tool_timeout_sec` above the longest command; `extras::check` requires `orbit_box` on, and never counts it as an extra on later turns, since a warm `thread/resume` keeps it. Calls arrive as `mcpToolCall` items and show like commands. The tool's description goes into the custom review instructions (`boxtool::Server::notes`), after any checks' results.
  - Claude: the review turn only adds `--mcp-config` with the server (alongside `--strict-mcp-config`), `mcp__orbit_box__run` in `--allowedTools`, and the description with `--append-system-prompt`. Later turns don't get it.
  - Antigravity has no per-run MCP option, and Orbit never changes its settings, so its reviews run without the tool and say so in the chat.
  - The tick (`Engine::close_boxes`) removes a review's container once the review is no longer active; Stop removes it at once (`close_box`), as does quitting. A tool call after that answers that the container is gone. Verified with codex-cli 0.162.1 (fake model, real Docker) and Claude Code 2.1.296 (fake API, sandbox on) running real commands in an `alpine:3.20` container.
- `docker version` and `devcontainer --version` are checked with the reviewers on connect (`Snapshot::dev_containers`). On Windows the CLI is started through `cmd /C`, since npm installs it as a `.cmd` script.
- Tested against a fake `docker` and `devcontainer` (`src-tauri/src/devcontainer_fixture.cjs`), which keeps containers as folders and runs commands with the host's shell. One test, skipped by default, uses the real tools: `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features real_docker -- --ignored` builds a recipe from `alpine:3.20` and checks the commands run as the recipe's user, in `/workspaces/<repo>`, without `.git` or network, and leave the worktree untouched.

### Model pinning

Every new review pins an explicit model and effort when queued. Orbit validates that pair against the connected account's catalog before enqueueing and preparation. Changing workspace Settings affects future runs only. Model selection uses the catalog's `model` identifier, not its display ID. How empty settings are resolved is described in the [user guide](user-guide.md#settings-and-when-changes-take-effect).

Orbit sends the pinned model, matching `review_model`, and reasoning effort on thread creation. It requires Codex's returned model and effort to match exactly and persists the confirmation before `review/start`. Every follow-up resumes with its pinned pair, verifies and saves the confirmation, and passes the same model and effort on `turn/start`. Missing/null or mismatched responses stop execution. Threads created during a stopped or rejected preparation are archived; if archiving fails, Orbit tries to unsubscribe and records the thread ID in the chat. Orbit does not request provider fallback or modify your Codex configuration.

For older chats missing a recorded selection, Orbit unsubscribes its idle thread before the first legacy resume so Codex can apply overrides (0.156.1 applies changed overrides to an idle loaded thread only after its subscribers detach). If another subscriber prevents that change, response verification stops the turn.

## GitHub

- Each sync lists each connected repository's open PRs with one request and fetches an individual PR only when it is new or has changed. A repository that fails to sync keeps its last-known PRs and shows an error while the others continue, and autopilot only acts on repositories that synced successfully in the current session.
- Before publication, Orbit checks that the PR is still open and both SHAs still match. GitHub does not offer an atomic compare-and-comment endpoint, so a commit can still arrive in the small interval between that check and the POST; comments always identify the exact reviewed SHAs.
- With **Watch CI** on, each poll is followed by `Engine::watch_ci` (`engine/watch.rs`), which reads each connected repository's CI with one GraphQL request (`ci::read`): the default branch's latest commit and the latest commit of up to 100 open pull requests, each with its `statusCheckRollup`. Orbit's own `orbit/review` status is dropped, so Orbit never reacts to itself. A commit with more than 100 checks keeps the page's `endCursor`, and `ci::read` follows it with `ci::more_query`, up to `MORE_PAGES` (20) further pages per repository; a commit whose checks weren't all read is `incomplete` and settles as running unless something failed, so it can open a problem but never close one. Repositories are read one at a time, after the sync, so a slow GitHub never holds up the review queue. A failed read keeps the last `RepoCi` with its error and leaves problems as they were. Results are applied under the state lock only if Watch CI is still on; otherwise they are dropped and watching stops as if it had been off.
- A stable marker in each comment and review reconciles ambiguous retries after a timeout or restart. A local instance lock prevents two Orbit processes from using the same state directory concurrently. This is local deduplication, not coordination across multiple computers.

## Isolation and its limits

Orbit fetches GitHub's PR head ref and the captured base commit into the configured clone, verifies the head SHA, and creates a detached worktree under its app-data directory. This changes Git metadata but does not check out or edit the original working tree. Git hooks are disabled for these operations. Temporary `refs/orbit/*` refs are deleted from your clone as soon as the worktree exists.

Each review gets its own Codex thread and working directory. Setup and agent commands use the Codex **workspace-write** sandbox, with network access disabled unless configured for that repository.

This is a **worktree plus the Codex OS sandbox**, not a VM or a Docker/devcontainer environment, unless the repository runs its setup and checks in its [dev container](#dev-containers). Then the pull request's setup and checks run in a container, but the reviewer itself still works in the worktree, and can only run commands in the container through Orbit's tool when the repository allows it. Otherwise it uses host-installed tools, the repository's manifests/lockfiles, and the user-configured setup command. Worktrees do not copy untracked dependencies or secrets from the original clone. Codex's local configuration, provider access, sandbox support, and managed policies still apply; this app does not claim to hide all host files or all inherited integrations from Codex, such as hooks and skills. Only configure repositories and setup commands you intend to run.

Extra tools (`src-tauri/src/extras.rs`, `src-tauri/src/engine/extras.rs`): the review's `thread/start`, and the `thread/resume` before a follow-up or the findings turn, send `extras::off` in their `config`: each MCP server that `config/read` (with the thread's `cwd`) reports switched off by name, and the features in `extras::FEATURES_OFF` (plugins, apps, browser use, computer use, tool suggestions, memories, image generation) off. The thread/start `config` is deep-merged onto the user's Codex config, so an empty `mcp_servers` wouldn't remove servers; each needs `enabled: false`. A cold `thread/resume` doesn't keep the thread's earlier overrides, so every resume sends them again. Before `review/start` or `turn/start`, `mcpServerStatus/list` for the thread must show every server `disabled`; otherwise, or if Codex can't list them, the review doesn't start (its new thread is archived) or the turn isn't sent. Codex's review mode runs on the thread's config, so its reviewer gets only Codex's standard tools. A scan (`extras::off_except_plugin`) keeps plugins on but switches off each other installed plugin (from `config/read` and `plugin/list`) and, inside each, every server name Codex lists without a thread but `codex-security`: Codex ignores a thread's `enabled` for a plugin installed from the user's account, but not its servers. The scan's thread must then show only `codex-security` on. Checked against codex-cli 0.162.1.

> [!WARNING]
> Because the agent can read files outside its worktree, a pull request can plant instructions in its diff that try to get local secrets quoted in the report. That is why automatic review and publication are restricted to repository insiders: pull requests from a branch in the repository itself, by an owner, organization member, collaborator, or trusted account. The setup command can also execute code from the pull request, such as package install scripts, so prefer options like `--ignore-scripts`. With network access enabled for a repository, both setup and the agent can reach the network.

A report is never published automatically when it contains text matching a well-known credential format, and publishing one manually requires an explicit confirmation. The scan is a best-effort backstop, not a guarantee: secrets without a recognizable format are not detected.

## Pull-request history

The Decisions page (epic #77, folding PRism into Orbit) reads every connected repository's pull-request history from GitHub. Reading it runs no model: it is all parsing. Only the optional write-ups below do.

- Reading (`src-tauri/src/engine/ledger.rs`): when Orbit starts, every 5 minutes after, and as soon as a repository is connected, one background read (`refreshing_ledger`, skipped while one runs) lists each repository's 100 most recently updated pull requests in any state (`github::recent_pulls`) and fetches, for each one not stored yet or updated since, and every open one on the first read, once an hour per repository (`ledger::FULL_REFRESH`, `Engine::ledger_full_at`, stamped only when that repository's read succeeds, so a failed one is tried again on the next read) and on **Read again** (`refresh_ledger_fully`), since an edited comment doesn't always update its pull request, the pull request, its conversation comments, reviews, comments on changed lines, commits and files (`github::pull_history`). A repository that fails keeps what it had and shows its error in `Snapshot.ledger`; a pull request that failed is fetched again next time. A pull request whose fetched form is unchanged isn't written again, and `ledger.version` goes up only when stored history changes.
- Storage (`src-tauri/src/ledger/store.rs`): one JSON file per pull request at `ledger/<owner>/<name>/<number>.json` in the data folder, not in `state.json`, replaced in one step. A comment whose text changed since the last fetch keeps its earlier text as a revision (the last 10), so a review edited in place for a new head still counts as two rounds. Files in an older stored form are skipped and fetched again. Each read removes the folders of repositories no longer connected.
- Piecing together (`src-tauri/src/ledger/`, a port of PRism's reading layer): `roles` says whether a comment is the builder's, a reviewer's or a person's, from its text rather than its account, since everything is posted as you; `orbit` reads Orbit's own published reviews from their hidden data, or their Markdown when the data was left out for size, plus their inline finding comments; `milo` reads the reviews a Codex Dot such as Milo posts, in every phrasing they have used; `replies` reads the builder's answers, Orbit's `Fixed F2 in abc1234` / `Declined F2: reason` and the older phrasings; `narrative` reads the description's Before, After, How and other sections and its epic and stage; and `assemble` turns those into rounds, claims, each finding's path from opened to its final state, the pull request's numbers, and flags worth a look (merged with a finding open, a disputed decline, a finding still open in two later rounds, merged before any review, what the reviewer couldn't check). Whether a finding was open at the merge, and whether any review came before it, is worked out from the rounds up to the merge only, so a fix or a review after it doesn't hide it. `get_decisions` returns the result for every connected repository, most recently updated first, each with its write-up if it has one; `refresh_decisions` starts a read now.
- Write-ups (`src-tauri/src/ledger/writeup.rs`, `src-tauri/src/engine/writeup.rs`, a port of PRism's writer): off by default (`settings.write_ups`). After each read, one background run (`writing_up`) writes up, newest first, each merged or closed pull request whose write-up is missing or was made from a different input. The input is the pieced-together history as text: the description by section, commits, files, where each finding ended up and the flags, then the known areas from earlier write-ups, then the rounds and comments in order with reviewers' commands, folded details and Milo's evidence sections left out, cut at 120,000 characters from the end. Its SHA-256, without the known areas, is what decides whether a write-up is current, so changing the writer or model redoes nothing. Codex writes in a read-only thread with no approvals, the workspace model and effort, the extra tools checked off as for reviews, and an output schema; Claude writes with `claude -p` with no tools, settings, MCP servers or saved session, and `--json-schema`. Codex waits while it isn't connected or a usage window is 90% full or more, and Claude while it isn't connected. `writeup::read` checks the answer: unknown kinds and repeats are dropped, a quote is kept only when it is found in the description, a review, a comment or a commit message (ignoring case and Markdown emphasis) and then links there, and finding notes are matched to the history's findings. Each write-up is saved at `ledger/<owner>/<name>/writeups/<number>.json`, and `ledger.version` goes up. A repository disconnected during a run is skipped: the run checks it is still connected before sending each pull request and again before saving the answer. A failure stops the run and shows in `ledger.write_error`; a pull request that failed twice from the same input is set aside until it changes or Orbit restarts. A turn has 10 minutes. The page builds its Rulebook (the `rule` decisions of merged pull requests, by area), Areas and the write-up items in Worth a look from the write-ups it gets with `get_decisions` (`src/decisionData.ts`); areas match whatever their case.
- Export (`src-tauri/src/ledger/export.rs`): `export_decisions` (one repository or every one) turns the stored histories into one Markdown file: Worth a look, the Rulebook (merged pull requests' rules) by area, and each pull request's chapter with its write-up, findings and flags. Text from pull requests and writers is shown as written (`export::inert`): outside code spans (paired as CommonMark pairs backtick runs of the same length) brackets, backslashes and unpaired backticks are escaped and `<` and `&` become entities, so HTML, images and links in it stay plain text; a test renders the results with `pulldown-cmark` to check. On the desktop, Rust owns the save dialog and the file's content, as with review reports (`storage::select_report_path`, `write_report`), so no general file-write API or frontend-supplied destination is exposed; over the remote API it returns `{fileName, text}` and the browser downloads it.
- Bit and Decisions: after each read and each saved write-up, `Engine::note_decisions` passes `buddy::to_decide` (each `act` flag, keyed by pull request, kind and finding, and each write-up decision marked `act`, keyed by a hash of its statement) to `buddy::observe_decisions`, which writes one `Decide` note per key it hasn't seen. `Feed.decisions_seen` keeps each key with when it was last in the history (to the day), so a key is never noted twice while it is there; it is forgotten 30 days after it leaves, or when its repository is disconnected. `Feed.decisions_since` holds when Bit started watching each connected repository, so only items newer than that are noted; keys are recorded even while Bit is off. A typed question's briefing (`ask::briefing`) carries `decisions`: whether write-ups are on, the 15 most recently updated pull requests with their flags, write-up summary and up to 6 decisions each, and up to 60 rules from merged pull requests, all as data. `writeUps.enabled` and `writeUps.writer` are in `ask::SETTINGS`.

## Persistence and recovery

- State is atomically replaced in `state.json` under Tauri's app-data directory (typically `~/.local/share/dev.orbit.review` on Linux). Invalid state is left untouched. Since the whole file is written on every change, each housekeeping tick prunes it (`engine/prune.rs`): a pull request no longer in `Snapshot.prs` keeps its newest 3 reviews (`KEEP_ROUNDS`), and a kept review's chat is cleared 30 days after it last changed (`KEEP_CHAT_DAYS`). A review that is active, has a worktree or clean-up pending, or is named by an approval or a Needs you item is never touched. A reopened pull request's loop then counts only the kept rounds.
- Failing CI is kept as `Snapshot.problems` (`problems.rs`): one record per thing that fails, keyed `ci:owner/name` for a default branch and `ci:owner/name#12` for a pull request, with a 20-entry timeline. `problems::observe` opens, updates and closes them from each read; a pull request's problem waits while GitHub's answer is for an older head, and closes because the pull request left only when the read listed every open one. Only default-branch problems are Needs you items. Their item key is `problem:<id>:<alerts>`, so each alert is announced once through the usual `Snapshot.announced` record and survives a restart. When to alert again is `alerts::raise` (ported from an earlier alert tracker): again only for a newer commit failing more checks, or after `REMIND_AFTER` (24 hours). A problem that passes and fails again within `FLAP_QUIET` (1 hour) of its alert reopens quietly: `problems::quiet_keys` keeps its item key announced meanwhile, and `alert_due` tells you if it is still red an hour after the last alert. Closed problems are pruned after `KEEP_CLOSED` (14 days), and at most `MAX_CLOSED` (100) are kept.
- Orbit tells agents through `Snapshot.ops` (`ops.rs`): one `Thread` per pull request (`pr:owner/name#12`, its one comment, kept across that pull request's problems so item numbers are never reused) and one per default-branch problem (`issue:<problem id>`, its `orbit` issue). After each CI read, `Engine::tell_agents` (`engine/ops.rs`, single-flight) runs `ops::refresh`, then sends what `ops::next` plans, one write at a time and at most `WRITES_PER_PASS` (10) per pass: post, edit, or for an issue a closing note then close (`state_reason` completed when it passed, not planned otherwise), or reopen. A passed problem's issue closes only `CLOSE_AFTER` (equal to `FLAP_QUIET`) after it closed, when it can no longer reopen as the same problem. Something new is posted only while `ops::may_post`, which reads the snapshot as it is now, not as of the last CI read: Bit is on and its rule (`comment_on_prs` or `open_issues`) is Do it, or Ask first with the thread `allowed` by the `tell_agent` command; **Watch CI** is on and the repository connected; and for a comment, the pull request is still followed (open, not a draft, from a trusted source). What is already on GitHub is kept true whatever the rule. Only an open problem or a passing close changes a thread's items; a problem closed for another reason leaves them as last seen, worded "when Orbit stopped watching", and the hidden JSON says `open` and `passed`. Bodies are deterministic, so an unchanged problem sends nothing, and end with a hidden `<!-- orbit-ops thread=<key> {json} -->` line (`<`, `>` and `&` escaped as in `orbit-data`). Check names are code spans with backticks replaced, and only `https://github.com/` links are linked.
- Agents answer on the same comment or issue. Before writing, each pass reads the replies on every posted thread whose problem is open (`github::replies`, up to 10 pages a pass), keeps those from trusted accounts (the signed-in user, trusted accounts, and the pull request's author when `trusted_source`) that aren't Orbit's own, and parses them with `claims::ci_lines`. `ops::hear` reads each reply once (`read_to`, a comment ID) and makes the latest line about a failing item its `Answer`, but only from a reply posted at or after the item's `heard_from`: GitHub's time for the write that first showed the item failing this time (`ops::shown`, from `Posted.updated_at` in `settle`, or `shown_at` when a failure came back without changing Orbit's text). A comment or issue found again after a post Orbit didn't hear back about (`looked`), or saved by a version that didn't read answers (no `shown_at`, so `read_answers` first fetches it with `github::get_comment` or `get_issue`), takes it from GitHub's copy instead (`ops::recover`): each item its hidden line shows failing since the same commit counts from when GitHub last took that text (GraphQL `lastEditedAt`, or `createdAt` if it was never edited; an issue's `updated_at` moves with every comment), not from the edit that brings it up to date. An edited copy can't say when an item first showed, and it may have been posted for an earlier failure of the same check, so answers from before that time don't count. An item that starts failing again drops its answer and its `heard_from`, so replies from before Orbit says so, edited or not, stay with the failure before. GitHub's `since` filters by when a comment was last edited but lists by when it was posted, so old comments edited later come before new replies: a thread keeps `read_since` until it has read that list to the end, going on from `read_page` (reading the last page again, as a deletion moves the rest back) and noting the latest edit seen in `read_newest`, which becomes the next `read_since`. `shown` moves `read_since` on to the earliest `heard_from` of the failing items, since no earlier reply is about them. For `Fixed I2 in <commit>`, `ops::to_verify` lists answers still `waiting` (or `not_on_branch` once the head moved), the one tried longest ago first (`checked_at`, set on every try, failed ones too), and a pass checks at most `CHECKS_PER_PASS` (5): `github::compare(commit...head)` says whether the commit is on the branch (`identical`/`ahead`), newer than the head Orbit read (`behind`, so it waits) or not (`diverged`, 404 not found), then `ci::check_at` reads that check at the commit; a failure counts at once, but a pass only once every page of the commit's checks was read, and otherwise it waits. Bodies show each answer and link the reply, but never repeat its text, and the hidden JSON gains `answer` (`kind`, `commit`, `check`). A `Need a person` answer on a failing item of an open problem is a `ci_question` Needs you item (`attention.rs`, keyed by the reply); `buddy::observe_ci` writes `ci` notes for new posts, closed issues, declines and fixes CI doesn't bear out (`ops::event_text`).
- Why a job failed is `logs.rs`. After each CI read, `Engine::read_failures` (`engine/watch.rs`) takes from `logs::wanted` up to `PER_PASS` (3) failing checks on open problems: links not tried yet first (default branches first), then those whose `retry_at` is due, the longest waiting first, so a log GitHub keeps failing on never starves the others. `logs::job_of` accepts only `https://github.com/<repo>/actions/runs/<run>/job/<job>` in the problem's own repository; anything else is kept with an error and never fetched. `logs::read` asks GitHub for the job (`repos/<repo>/actions/jobs/<id>`) and its log (`.../logs`, plain text through `github::api_text`), and `logs::understand` turns them into a `Failure`. `logs::failed_step` picks the step most likely to have failed the job, as GitHub's answer doesn't say which steps could fail: the first marked `failure` or `timed_out` after which none of the workflow's own steps (not `Set up job`, `Complete job` or `Post ...`) succeeded, so a step that continued on error is usually passed over; otherwise the last one marked failed. `section` takes the log lines whose times fall within that step's `started_at` and `completed_at`, to the second, so an error annotation from an earlier step that passed is never shown; without those times, the whole log is checked and its last step shown (`last_step`). As GitHub gives step times only to the second, and the log marks no step's end (a composite action echoes several `##[group]Run` commands in one step), `own` leaves out any second that another step that ran also spans, except, in the failed step's last second, its lines up to its own last line when its command failed (`##[error]Process completed with exit code`) and no other command starts before it. `tail` takes the step's lines up to its last `##[error]`, without the commands GitHub echoes in `##[group]Run` groups, without times, ANSI colours, control characters, blank lines or group markers, the last `MAX_LINES` (20), each cut to `MAX_LINE` (240) characters. `credential_kinds` runs on the step name and all the step's seconds (or the whole log) before anything is left out or cut; a match keeps only `held`, so no part of a secret, such as the body of a private key whose first line is outside the excerpt, is saved or shown. A 404 or 410, or a 403 that isn't a rate limit, is kept as an error and not asked again. Anything else goes through `logs::retry_later`: the failure records the error, `tries` and `retry_at`, a minute doubling up to `MAX_RETRY` (an hour), as GitHub asks when it doesn't say how long to wait. After a rate limit (`logs::rate_limited`: a 403 or 429 saying so), the failure is marked `limited`, the pass stops, and `wanted` gives nothing until its `retry_at`, so no log is read until the wait is over. What was read is `Snapshot.failures`, keyed by the job link (a rerun is a new job; `logs::record` replaces an earlier try), and `logs::prune` keeps only links failing on open problems. Before planning, `ops::explain` copies each failure onto the failing item with its link (`Item.why`), and `items_text` shows the step and lines under the first `MAX_WHY` (5) failing items of an open problem: the lines in a fenced block longer than any backtick run in them, indented into the list item, with `<!--` broken up there and in every code span so nothing a log says can start a hidden line. The item's own line is unchanged, so replies still find it.
- Rerunning bad luck is `reruns.rs`. `logs::understand` also sets `Failure.flaky` from the failed step and its own lines (`logs::flaky`): no failed step, a lost runner (`LOST`), `Set up job`, a `Run actions/checkout@`, `actions/setup-` or `actions/cache@` step, or a network or registry error (`NETWORK`); a job whose log GitHub won't give is judged from its steps alone. Only the step's own lines count, without the commands and settings GitHub echoes in `##[group]Run` groups (`logs::output`), so a network error an earlier step got past, or one a command only names, doesn't excuse a test failure. Each `Item` keeps `reruns` (a `Rerun` per job link it tried: `done`, `already`, `lasting`, `error`, `tries`, `retry_at`, `failed_again`, `unsure`) and `rerun_ok`, the job link you tapped Rerun for; `ops::items_from` clears both when the item moves to a new commit, so `MAX_RERUNS` (2) is per check per commit. `reruns::all` plans a `RerunJob` write for each failing item whose current job's failure was read and looks flaky, that isn't already done or `lasting`, with fewer than `MAX_RERUNS` done, on an open problem about the latest commit Orbit knows (the pull request's `head_sha`, or the default branch's head in `Snapshot.ci`), that Orbit is `ops::watching`, when `ops::rule_allows` the rule (`rerun_flaky` for the first, `rerun_again` for the second, allowed by `rerun_ok`) and any `retry_at` is over. `engine::ops::plan` puts reruns before posts, so Orbit's text says it reran a job. Before each rerun, `reruns::look` reads the job (`actions/jobs/<id>`), and `reruns::ours` checks that it is the planned check's job at the item's commit: its `head_sha`, and a `name` that is the check's, or that the check's ends with after `" / "`. Anything else is `Look::Elsewhere`, kept as `lasting` and never sent. It then reads every page of the job's run's latest jobs (`runs/<run>/jobs?filter=latest&per_page=100`, at most `MAX_PAGES` of 10); `reruns::page_of` fails closed on a page without `total_count` and a `jobs` list, and an empty page before `total_count` is reached is an error too, so a partial list never reads as Ready. A job of the same name with a later `run_attempt` means it was already rerun (`Look::Already`, recorded as done, no write); a job still running means GitHub would refuse it (`Look::Running`, which waits like a failure). Otherwise the pass plans again under the lock and, under that same lock, records the write in the journal and marks the rerun `unsure` (`reruns::sending`), flushes, and `POST`s `actions/jobs/<id>/rerun` (`github::rerun_job`). `reruns::settle` marks the rerun done, clears `unsure` and returns `Event::Reran` for Bit, or keeps a 404, 410, 422 or a 403 that isn't a rate limit as `lasting`, never asked again, and backs off otherwise (a 409 too, as GitHub may say that only while the run starts again); `unsure` stays unless the error is lasting, as a request that failed may still have reached GitHub. While a rerun is `unsure`, `reruns::candidate` plans nothing new for its item, and `reruns::all` plans a look for it first (`Job.unsure`), whatever the rules or Bit, once any `retry_at` is over: a newer try means it went through (done, `Event::Reran`), and none means it didn't, so `unsure` is cleared and the rules decide again. That, and the look before every rerun, is what keeps a cut-off rerun from being sent twice; `ops::interrupted` marks the journal entry failed as for posts. While the rerun runs, the problem is unchanged (`problems::see` waits on `Running`); a new try that fails has a new job link, its log is read afresh, and `reruns::noticed` marks the last done rerun `failed_again` once that log is read and returns `Event::FailedAgain` (with `ask` when the second rerun waits for a tap), unless Orbit is about to rerun it on its own. `reruns::text` puts one line under the item (reran, reran a second time, already rerun, or failed again so likely real), `item_line` adds "after a rerun" to a check that passes, and `data` adds `reruns` (the count done) to an item only when there is one, so older bodies are unchanged.
- A pull request whose checks passed before its base moved on is a `ProblemKind::BaseMoved` problem, keyed `base:owner/name#12`. The CI query reads when each check began (`checkSuite.createdAt` for a check run, `createdAt` for a status) and when the default branch's latest commit was made (`committedDate`); `ci::add_checks` keeps the earliest start of the checks that passed as `CommitCi.ran_at`, cleared when one of them has no time. `problems::behind` says whether a followed pull request into the default branch has checks that passed having begun before that commit (None when it can't tell), and for one whose checks pass `problems::see_base` opens the problem (with `base` and `base_sha`), notes the base moving again or a newer head still behind, closes it as passed (`closed_sha`) once the checks pass having begun after it, and closes it when they fail. Before any of that, one whose `base` is no longer the default branch's name or the pull request's base, as after a rename, is closed, so one about the new base can open in the same read. It closes with its pull request like a failing one. It shares the pull request's thread (`pr:owner/name#12`): `ops::items_from` gives it one item of `ItemKind::BaseMoved`, whose `check` is the base branch, numbered once and reused if the base moves on again; `comment_body` and `base_line` word it, and the hidden JSON gives it `kind` and `base` instead of `check`, so older bodies are unchanged. `to_verify` skips it, as CI settles it, and `Item::name` names it in Bit's notes and the **Needs you** question item.
- A repository where no CI runs on pull requests is a `ProblemKind::NoCi` problem, keyed `setup:owner/name`. After the CI read, logs and breaks, `Engine::read_setups` (`engine/watch.rs`) takes from `workflows::wanted` up to `PER_PASS` (2) repositories whose default branch head (`RepoCi.head.sha`) or name Orbit hasn't read its files at, or whose read failed and is due again, those tried least first. `workflows::read` asks GraphQL, by `<sha>:<path>` expressions, for the blobs directly in `.github/workflows` (only `.yml` and `.yaml`), the names at the top and `package.json`, and `workflows::understand` turns that into a `Setup` in `Snapshot.setups`: each workflow's `OnPulls` from a small reader of its `on:` (`pull_request` or `pull_request_target`, or `push` for every branch, with `branches-ignore`, or with a `branches` pattern, is `Yes`; `push` only to named branches or tags, and other events, are `No`; anything outside the shapes it reads, such as tabs, several documents, flow mappings or unknown filters, is `Unknown`, as is a truncated or binary file), another CI service's files from `OTHER_CI`, and the proposal. `workflows::record` keeps an error with a backoff from a minute up to `logs::MAX_RETRY`. `Setup::verdict` is `Covered` (a `Yes` workflow, or another service's files), `Unknown`, `NoWorkflows` or `NotOnPulls`, and `problems::see_setup`, called after each CI read and each files read, acts only on a `Setup` read at the head and branch name Orbit sees now; the `NoCi` item's `check` follows a renamed branch. Checks on a followed pull request's latest commit, or on the default branch when there are no workflows, are kept as `Setup::ran`, which `record` carries across reads, so once Orbit has seen checks it never claims that nothing runs them. It opens the problem only for `NoWorkflows` or `NotOnPulls` with no `ran`, and only once `QUIET` (10 minutes) has passed since `read_at`, so another service's checks have time to show up; an open one follows the head (`sha`, `branch`, `found`, noting a change in what Orbit found). `Covered` closes it as passed (`closed_sha`), and `Unknown` or `ran` close it otherwise, with a timeline note that names the file and a reason in Orbit's own words, as the reason goes on GitHub. It isn't a **Needs you** item. Its thread is an issue (`issue:<id>`), with one item of `ItemKind::NoCi` whose `check` is the branch; `to_verify` skips it. Posting it has its own rule, `rule_of` mapping it to `propose_ci` (Ask first by default), and `ops::offer` sets `Thread.offered` and returns `Event::Offered` once, for Bit's note, while the rule asks first. `proposal_body` words the issue, with the workflow from `workflows::propose`: GitHub's own actions only (`setup-node` with `cache: npm` only for an npm lock file, and `package-manager-cache: false` otherwise, as it caches on its own when `package.json` names a package manager and then fails without a lock file or before Corepack has set up pnpm or Yarn), commands only from Orbit's own lists (the `SCRIPTS` a `package.json` has, else `check`; `cargo test`; `go test ./...`), and the branch in `push` only when it needs no quoting, so the repository's text never reaches the YAML. `closes` lets it close at once rather than after `CLOSE_AFTER`, as completed when passed, and the hidden JSON gives the thread kind `no_ci` and its item `kind` and `branch` instead of `check`.
- Self-hosted runners are `runners.rs`. At the end of `Engine::watch_ci`, after `tell_agents` so telling agents never waits on it, `Engine::read_runners` (`engine/watch.rs`, guarded by `reading_runners`, and only with Watch CI on) takes from `runners::wanted` up to `PER_PASS` (4) places: each connected repository (`PlaceKind::Repository`) and each account that owns one (`Owner` until read), those never read first, then those read longest ago, each again `EVERY` (5 minutes) or once a failed read's `retry_at` is over; a `Person` is never read again. `runners::read` asks `repos/<repo>/actions/runners` and `repos/<repo>/actions/runs?status=queued` (100 each) for a repository; for an account, `users/<login>` says whether it is an `Organization` (then `orgs/<login>/actions/runners`) or a `Person`, so a 404 is never taken to mean "not an organization". `runners::seen` keeps a 404, or a 403 that isn't a rate limit, as `Place.unseen` in Orbit's words (admin rights on the repository, or an organization owner with `admin:org`), never as "no runners"; anything else is an error that `runners::record` keeps with the place's earlier read, backing off from a minute up to `logs::MAX_RETRY`, and after a rate limit the pass stops. `runners::waiting` keeps the queued runs whose latest try (`run_started_at`, else `created_at`) began at least `STUCK` (30 minutes) ago, the longest first, with links only to `https://github.com/`. For a repository read that worked and is still connected, `problems::see_waiting` opens, updates or closes its `ProblemKind::Waiting` problem (key `wait:owner/name`, `Problem.waiting`), which `needs_you`, alerts like a failing default branch (`REMIND_AFTER`, and `FLAP_QUIET` when it comes back) but is never worse, and closes with "No runs wait for a runner now.". `ops::refresh` skips it, so it has no thread and nothing reaches GitHub. `attention::items` makes it an `AttentionKind::RunsWaiting` item from `problems::waiting_text` and `runners::seen_text`, which says what Orbit sees of the runners the repository's runs could use (its own and its organization's): none, all offline, all busy, or some free, which suggests a label none has, and that it can't see all of them when a place is `unseen` or has more than one page. What was read is `Snapshot.runners`; `runners::prune` keeps connected repositories and their owners, and `stop_watching` clears it.
- What broke a default branch is `broke.rs`. After each CI read and the logs, `Engine::read_breaks` (`engine/watch.rs`) takes from `broke::wanted` up to `PER_PASS` (2) open default branch problems with no answer yet (`Problem.broke` empty, or not `done` and its `retry_at` over), those not tried first. `broke::read` asks GraphQL for the history of the first commit Orbit saw failing since the branch last passed (`since_sha`, which `problems::observe` moves to the new failure, clearing `broke`, when a problem comes back within `FLAP_QUIET`; `broke::record` keeps an answer only while `since_sha` is still the commit it was read from), `HISTORY` (40) commits at a time, each with its first parent, the first page of its checks and the pull requests associated with it; `broke::commits` turns them into `Seen` (state by `ci::add_checks` and `ci::settle`, so Orbit's own status is left out and a commit with unread checks is never Passing; `pull`, the merged pull request whose base is the default branch). `broke::walk` follows first parents only, so a merged branch's own commits, which may have passed on their pull request, never count, for at most `BACK` (20) commits, to the first that is Passing; when the chain leaves what was read it returns `Walked::Need` and `read` asks again from there, at most `REQUESTS` (3) times. The commits from the oldest Failing one after the green commit back to just after it are where it broke (`Broke.commits`, newest first, with `pulls`, `direct` for those with no pull request, and `pull` when one pull request accounts for all of them, as for a squash, a merge commit or a rebase). No green commit within `BACK`, the branch's first commit, GitHub no longer having the commit, or GitHub no longer having any of them failing are `done` with an `error` and no commits. Anything else GitHub doesn't answer backs off from a minute up to `logs::MAX_RETRY`. `broke::markdown` puts the sentence after the status line of Orbit's issue (`ops::issue_body`), so the issue is edited once it is found, `broke::text` adds it to the **Needs you** item (`attention.rs`), and `brokeText` in `src/Operations.tsx` shows it on the problem.
- Each write is a `Write` in `Snapshot.journal`, recorded as `sending` and flushed to disk before it is sent; if the flush fails it isn't sent. `ops::settle` records GitHub's answer on the entry and the thread, after checking that the answer holds Orbit's marker (`github::posted`). At the start of a pass, `ops::interrupted` marks entries still `sending` as failed, since nothing is in flight then, and sets `unsure` on the thread of a cut-off comment or issue; a failed create sets it too. An `unsure` thread that isn't known to be posted plans `Action::Find` before anything else, whatever its problem's state or `may_post`, and `ops::looked` adopts what it finds, to be brought up to date like any posted thread. Every write that creates something (a comment, an issue, a closing note) first looks for its marker among `login`'s comments or issues (`github::find_comment`, `find_issue`) and edits or keeps what it finds, so a write GitHub got before a crash is never sent twice; edits and state changes are idempotent. After a search that finds nothing, the pass plans again under the lock and sends only if the plan is unchanged, so a rule or setting changed during the search counts. A search reads at most `FIND_PAGES` (100) pages of 100, and only a page that isn't full proves there is nothing more: a search that reaches the cap on full pages is an error, never "none". A failed write sets `retry_at`, a minute doubling to at most `MAX_RETRY` (1 hour), and ends the pass; `tries` goes back to 0 only when a write succeeds or a search adopts what it finds, so a failed create's search that finds nothing keeps the streak; a 404 or 410 on something already posted marks the thread `gone` and Orbit stops writing to it. A thread is kept while its problem is, or while Orbit still has work for it (`in_use`: `unsure`, an issue it hasn't closed, or a comment whose pull request is still in `Snapshot.prs`, `gone` or not, so a deleted comment isn't posted again), and `ops::pinned` keeps those threads' problems past `KEEP_CLOSED` and outside the `MAX_CLOSED` cap in `problems::prune`, so an open issue can still be closed with its note and a comment keeps its item numbers; the journal keeps at most `MAX_JOURNAL` (200) entries for `KEEP_CLOSED`.
- Active runs become visibly interrupted after restart instead of being silently retried.
- A state-write failure turns Autopilot off; after resolving it, re-enable Autopilot to resume automatic reviews.
- An automatic review that can't be queued (`Engine::queue_automatic`), such as when its checkout is gone, is recorded in `Snapshot.queue_failures` with the reason, shown as a **Needs you** item, and tried again each `queue::QUEUE_RETRY` (1 minute, `Engine::queue_retry`) rather than on every 200 ms tick.
- Threads and worktrees are retained for follow-ups. Orbit removes a review's worktree automatically once its pull request is no longer open in a connected repository (merged, closed, or the repository was disconnected), and when a review fails or is stopped before it starts; the chat stays readable, but follow-ups then need a new review.
- Manual worktree removal checks registered ownership and eligibility under the Git lock, persists cleanup intent before touching files, and recovers pending removals after restart. Interrupted automatic cleanup rechecks PR closure on restart, independently of initial inbox sync.

## Buddy

Bit's notes are written by the engine, not the UI, so they cover what happened while the window was closed. `src-tauri/src/buddy.rs` holds the settings (`Buddy`, checked in `Settings::validate`), the feed, the mood, the fixes and their rules, the quick answers, and the note templates for each tone.

- After each change, `Engine::flush` runs `attention::announce` (the once-only Needs you notices) and then `buddy::observe` with the items that just opened. `observe` compares each loop's `review_loop::state` with what Bit last saw (`SeenLoop`: rounds started and finished, stopped, extra rounds) and writes one note per change, plus one per new Needs you item. The first look at a workspace, and a loop it meets with more than one round behind it, are only recorded, so an upgrade or a PR returning to the inbox doesn't retell old rounds.
- The feed (`Snapshot.buddy_feed`) is saved in `state.json`, keeps the last 50 notes, and numbers them so the UI has stable keys. Loops are recorded even while the buddy is off, so turning it on doesn't replay them.
- The mood is worked out in `attention::shown` from the same snapshot every client sees, and is never saved.
- Fixes: `attention::items` gives each item the `Fix` that resolves it, if one of Orbit's own controls does (`ContinueLoop`, `ReviewAgain`, `Publish`, `SyncNow`, `TurnOnAutopilot`, `CheckConnections`); approvals have none. A `Disconnected` item (`connection:<key>`) opens for each of `guide::connections` other than GitHub (whose problems are the sync items') that has an error, isn't ready and is used by a connected repository: Codex, Claude, Antigravity, or the dev container tools. Its `CheckConnections` fix runs `Engine::check_connections` (`engine/setup.rs`): the reviewers' checks, `connect`, then a sync, as Settings' Reconnect does; it succeeds once the item has closed. Like `TurnOnAutopilot`, it has no rule and always waits for a tap. `Publish` is only offered for a current report that automatic publication wouldn't hold, so never for a credential-flagged one or one from an untrusted source. The UI shows the fix as a button on a note or answer line whose `key` names an open item, and runs it with `use_fix` (`engine/fixes.rs`), which looks the item up again by key, uses the control as the app's own button does, and writes a `Fixed` note.
- Do it: in `Engine::flush`, an item that just opened whose fix's rule is `do_it` (`buddy::will_fix`, only while Bit is on) gets a `Fixing` note from `observe` instead of a `NeedsYou` one, skips the desktop notification, and joins `Engine::fixing`. The next tick's `do_fixes` runs each in its own task and writes `Fixed`, or, when the fix fails while its item is still open, a `NeedsYou` note with the item's key and a notification. A queued fix runs only while it is still Bit's (`still_mine`: the item is open about the same report with the same fix, and `will_fix` still agrees), checked under the same state lock as the change (`continue_loop_if`, `enqueue_if`); one whose item closed meanwhile is dropped. Bit publishes as `publish::By::Bit`, which repeats that check and applies automatic publication's trust and credential holds to the fresh PR before every write, independent of the publication switch, for buttons and Do it alike. `TurnOnAutopilot` changes settings, so its rule is always `ask_first`. Sync now waits for a sync already running (`poll_lock`), checks again, then syncs (`poll_holding`), and counts as done only once the item has closed. `attention::announce` judges a report being published as still ready, so a publication that fails doesn't make its item new again and Bit tries a Do it fix only once.
- Quick answers: `ask_buddy` writes an `Answer` note with the question and one `NoteLine` per thing it lists, worked out from the snapshot (`buddy::ask`), so every window sees the same conversation. No model is involved.
- Setup help (`guide.rs`): **Help me set up** (`Question::Setup`) first runs `Engine::look_up` for each connected repository's copy, and lists your GitHub repositories only while none is connected. `guide::setup` turns the snapshot and lookups into lines and proposals, the same `Proposal`s typed answers offer, each checked through `ask::set_up_proposal`, `ask::autopilot_proposal` or `ask::answerer_proposal` as an answer's would be: first Bit's own answerer (`guide::bit_ready`, the one readiness check typed questions use too), and while it isn't ready, its fix plus either an `answerer_proposal` for each other sign-in that is ready or, with none, a fix for each sign-in and an `answerer_proposal` for Ollama and each API; then for each other connection that is off (one only Bit uses is covered by Bit's lines), the button `guide::fix` picks from its `Remedy` (`SignIn` for GitHub or Codex when their error says they're signed out, `Install` for one that can't start and for the reviewers, opening its page from `guide::PAGES`), then one `CheckConnections` proposal, up to 3 `connect` proposals when nothing is connected, then per repository a setup command from `setup::suggest` (the first file of `setup::SETUP_COMMANDS` the copy has, with network access) when it has none and its reviewer can run one, and automatic reviews when they're off, then global autopilot. `Guide::offer` drops a proposal already offered. `Guide::to_do` counts what's left for the answer's opening line. `Engine::pick_bit_answerer` (`engine/settings.rs`) switches `buddy.answerer` to `guide::pick_answerer`'s choice, the one ready sign-in (Codex, Claude, Antigravity) while Bit is on and its answerer is a sign-in that isn't ready, and writes a `Fixed` note saying so; it runs before **Help me set up**, before a typed question, and at the end of `check_connections`. A typed question Bit can't answer gets `buddy::cant_answer`'s note with `guide::bit_setup`'s lines and buttons instead of an error. `save_repository` runs the whole save in a task of its own (`carry_on`), so it finishes even if the caller goes away. For a new repository with an empty path, it first gets Orbit's own copy through the same `Engine::own_copy` download a `connect` proposal uses, holding `cloning` until the repository is connected, and keeps it up to date. When a repository is added, from `save_repository` or a `connect` proposal, `Engine::note_connected` writes a `Connected` note with `guide::connected`'s steps for just that repository, if Bit is on. `clone_facts` passes the suggestion to typed questions too, as the copy's `suggestedSetup`.
- Typed questions: `ask_buddy_anything` (`engine/ask.rs`) writes a pending `Answer` note (`buddy::asked`), then asks `Buddy::answerer` (`buddy::ANSWERERS`: `codex`, the default, `claude`, `antigravity`, `ollama`, `openai`, `anthropic` or `google`; the reviewers are checked with `ModelSelection::validate_for` and the model and effort `Settings::selection` gives that reviewer). Codex gets a thread of its own with the Codex model and effort from Settings, `sandbox: read-only`, `approvalPolicy: never` and an empty `bit` folder in Orbit's data folder as its working directory. Its `config` (`ask::thread_config`) turns off web search, the extras (`extras::off`, above) and the standard tools in `ask::TOOLS_OFF` (commands, images, sub-agents, goals, hooks), for this thread only. Before the turn starts, `mcpServerStatus/list` for the thread must show every server `disabled`; otherwise, or if Codex can't list them, the thread is archived and the question isn't asked. One question runs at a time (`Engine::asking`). `ask::instructions` tells Codex who it is, the tone and personality, and that the state is data; `ask::prompt` sends the question with `ask::briefing`, a summary of the snapshot that leaves out trusted accounts, clone paths and PR bodies, hides a setup or check command the credential scan flags, and clips titles. Before the prompt is built, `Engine::look_up` (`engine/setup.rs`) adds `ask::Lookups`: each connected repository's copy as `setup::clone_facts` reads it (telltale files from `setup::TELLTALE_FILES`, and `package.json` script names and package manager only when short and plain), and one page of `github::recent_repositories` minus the connected ones, with a 10-second limit; a look that fails puts its error in the summary instead. Claude Code and Antigravity get the same instructions, prompt and `ask::output_schema` (`start_cli_answer`), Claude in the same `bit` folder and Antigravity in `bit-antigravity`, emptied before each question, and their `structured_output` goes through the same `ask::answer` as Codex's text. Claude runs with `claude::write_up_args` (no tools, no setting sources, `--strict-mcp-config`, no session saved) and the prompt on standard input. Antigravity can't turn its tools off or take separate instructions, so the instructions lead the prompt, and it runs as a review turn does: `--sandbox`, `antigravity::check_settings` before it starts, and `init` must report a permission mode from `antigravity::ASKING_MODES`. For both, `init` must also report the requested model, as for reviews; otherwise the question ends without an answer. The process is kept in `Asking::running`, so ending the question (the answer, the 3-minute limit) kills it with its commands. Only a Codex question ends when Codex disconnects (`end_codex_question`). `guide::connections` marks the answerer's connection `for_bit`, so Claude, Antigravity or Ollama shows in setup help while Bit answers with it. Ollama (`ollama.rs`, `buddy::Answerer::Ollama`) is reached over HTTP with `reqwest`, without a proxy: `check_ollama` lists `/api/tags` at `buddy.ollamaUrl` (5-second limit) while Ollama answers Bit, at startup, on Check again and whenever the answerer or address changes (`update_settings`), into `Snapshot::ollama` and `ollama_models`; none listed counts as not ready. A question checks the chosen `buddy.ollamaModel` is listed, then `start_request` posts one `/api/chat` (`stream: false`, the instructions as the system message, `format: ask::output_schema()`), held as `Asking::request`, which aborts the request when the question ends; an answer whose `model` isn't the one asked for is dropped. `buddy.ollamaUrl` must be `http://` or `https://` with a host and no credentials (`ollama::validate_url`); it and the model aren't in `ask::SETTINGS`, so an answer can switch to Ollama but never point it somewhere else. API keys (`api.rs`, `buddy::Answerer::Api`: `openai`, `anthropic`, `google`) are saved with `set_api_key` into the OS password store through the `keyring` crate (service `dev.orbit.review`, entry `<provider>-api-key`), behind `api::Secrets` so tests use a store in memory; `Snapshot::api_keys` only records `saved` (kept between runs, so the store is only opened when a key is used), the latest check and the models. `check_api` (held under `Engine::api_lock` with saves) lists the provider's models with the key and keeps only those that can answer in a strict JSON schema (OpenAI `/v1/models`, by name, since OpenAI doesn't list what each model supports: GPT-4o after its first version, GPT-4.1, GPT-5 and later, o1 and o3 and later; Anthropic `/v1/models` unless its `capabilities.structured_outputs.supported` is false; Gemini `/v1beta/models` with `generateContent`, Gemini 2 and later), after a save and, for the answerer's provider, at startup, on Check again and when the answerer changes; a key gone from the store counts as not saved. A question then sends one request through `start_request`: OpenAI's Responses API with a strict `json_schema` text format and `store: false`, Anthropic's Messages API with `output_config.format` (no fallbacks, so the model stays the one you chose), or Gemini's `generateContent` with `responseJsonSchema`; never tools. The reported model must be the one asked for or a dated version of it (`api::same_model`), and refusals, cut-off answers and a key the provider turns down end the question with a reason that never shows the key. The model choices (`buddy.openaiModel`, `anthropicModel`, `googleModel`) aren't in `ask::SETTINGS`. The names offered to connect are kept on the question (`Asking.connectable`) so the answer is checked against them. The turn's `outputSchema` (`ask::output_schema`) asks for `{answer, proposals, memory}`. `Engine::event` routes the thread's notifications to `answer_event` before scans and reviews; `turn/completed`, a 3-minute timeout, or a Codex disconnect ends the question, and the thread is archived (interrupted first if unfinished). `ask::answer` refuses an answer the credential scan flags, clips it, and keeps only proposals for an allowed action that apply now (at most 3): a known PR whose loop can be stopped or continued, nothing running for Review again, `attention::may_publish` for Publish, for Change settings a change to one of `ask::SETTINGS` (never trusted accounts or repository settings) that parses as a `SettingsPatch`, passes `Settings::validate` and changes something, and for Set up repository a `setup::RepositoryPatch` built by `setup::patch` from `setup::REPO_SETTINGS` (one-line commands of up to 500 characters that the credential scan doesn't flag and `setup::allowed` accepts: the setup commands Orbit suggests and other known install and test commands, each with only the value-free switches `setup::KNOWN_FLAGS` lists for it, `npm`, `pnpm`, `yarn` or `bun run <script>`, or `make [target]`, with no options, joined by `&&` or `||`; anything else is typed in Repositories, the round and approval limits Repositories offers) for a connected repository it changes, or for one the summary offered to connect (`connect: true`), whose result passes `Repository::check`. A pending note found at startup says Orbit closed before it could answer (`buddy::recover`).
- Bit's memory: `Feed.memory` (`buddy::Memory`, saved in `state.json` with the feed) holds general lines and lines per repository. The briefing includes it with its limits, and `ask::instructions` says what is worth keeping. An answer's `memory: {forget, remember}` lists lines with a repository or null; `ask::memory_change` turns each into one line of at most 200 characters with no control characters, drops a remembered line the credential scan flags, and keeps a repository only if it is connected (or, for forgetting, already in memory), at most 10 changes per answer. `buddy::answered` applies them only while the question is still pending (`change_memory`): forgets first, so a full place can make room, skips a line already kept (ignoring case), and refuses one beyond `MEMORY_GENERAL` (20) or `MEMORY_PER_REPO` (10) as `full`. The changes made are recorded on the answer note. `forget_memory {repo, line}` and `clear_memory` let you remove lines from Settings; each advances `Engine::memory_generation`, and an answer whose question was asked before that drops its memory changes (its text and buttons still show), so it can't bring back what you forgot.
- Answer buttons: `use_proposal` runs a proposal only when tapped, and once: it claims the button in `Engine::using` under the state lock before any await, refuses a second tap while the claim lasts, marks it `done` before the claim ends, and drops the claim on failure so it can be tapped again. It goes through the same engine paths as the app's controls, which check again: `continue_loop`, `stop_loop`, `enqueue`, `publish_by(By::Bit)` (the fresh trust and credential checks before every write), a sync under `poll_lock`, `update_settings` with the stored patch completed against the settings at tap time (`ask::complete_patch`, so a write-ups change keeps the other write-up setting as it is then), refusing a patch that touches trusted accounts, and `Engine::set_up_repository` for Set up repository: a connected repository gets the patch through `commit_settings`; a button without `connect` fails for one disconnected since; otherwise, under `cloning`, Orbit runs `gh repo clone` into `downloads/<owner>/<name>` (`setup::download_folder`, cleared first) and moves the finished copy to `clones/<owner>/<name>` in its data folder (`setup::clone_folder`) unless that folder exists, so a download cut short is never connected, then checks the copy's origin (`validate_checkout`) and, under the state lock, connects it with `Repository::new`'s defaults, keeping the copy up to date, plus the patch, or gives the patch to the repository if it was connected meanwhile, and starts a sync.
- Sign-ins (`engine/sign_in.rs`): a `SignIn` proposal runs `Engine::sign_in`, one at a time per service (`Engine::signing_in`), and never counts as done. GitHub runs `gh auth login --web` without a terminal, reads the code and page from what it prints (`github_prompt`, in either wording gh uses, depending on its clipboard setting), writes a `SignIn` note with the code and an `OpenPage` button, then waits up to 15 minutes in the background; on success it runs `gh auth setup-git` and `check_connections`, and a note says how it went. Codex starts `account/login/start` with `chatgptDeviceCode` on the running app-server, which answers with the code and page; `account/login/completed` hands the result to the waiting task over a channel (`Engine::codex_login`), which connects again. `disconnected` drops a waiter started on the connection that went away (`codex_login_lost`), so its task ends and a new sign-in can start as soon as Codex is back. When a sign-in ends, its code note loses the code and its button. `OpenPage` proposals never reach the engine: the app opens them where you are, the desktop window through `open_github`, which accepts only `guide::may_open` links (GitHub, `guide::PAGES`, and the sign-in pages). `ask::HELP_ACTIONS` are never accepted from an answer.
- The colour, hat, look, tone, rule, fix, question and action lists, and the memory limits, live in `buddy.rs` and the app (`src/Bit.tsx`, `src/types.ts`); `test-fixtures/buddy-options.json` holds them once, and tests on both sides check against it. An older state file without buddy settings gets the defaults, and a value a newer Orbit saved that this one doesn't know falls back to the default.

## Concurrency and locking

The engine's locks, what each protects, and the order to take them in are documented on the `Engine` struct in [`src-tauri/src/engine/mod.rs`](../src-tauri/src/engine/mod.rs). In short: one connect, sync, publication, and worktree removal at a time; Git commands against your clones are serialized; and `std` mutexes are never held across an `.await`.

Narrow updates preserve unrelated settings. Global settings and repository operations are ordered independently, so slow checkout validation cannot delay turning Autopilot off. Filesystem validation runs off the async workers with a bounded wait.

## Process lifecycle

On exit, Orbit closes the app-server's stdin and terminates it. Unix process-group termination also cleans up its descendants. Windows uses child-process termination; Windows packaging and descendant cleanup need platform validation.

## Frontend

- The frontend has no generic shell/filesystem/RPC endpoint. Native commands are narrowly scoped (see the allowlist in `src-tauri/src/lib.rs`); CSP restricts network access, raw Markdown HTML is not executed, and remote Markdown images are not fetched.
- Report export is generated and written in Rust; the frontend supplies only a review ID.
- Browser access (`src-tauri/src/remote.rs`, `src/remote.ts`, `src/RemoteAccess.tsx`) is off until **Settings → Use Orbit from other devices** turns it on; `remote.json` in Orbit's data folder keeps that choice and the port. It serves the same frontend and the same command allowlist on `127.0.0.1` only, for `tailscale serve` to publish. `remote::DESKTOP_ONLY` lists what a browser cannot run: `open_github`, and the access controls themselves, so a browser can't widen or keep its own access. Every `/api` call needs the access token from `remote-token`. The token travels in the link's fragment and an `Authorization` header, never a URL or cookie. **Make a new link** replaces the token and restarts the server, which ends every open event stream. Turning access off replaces the token too, so an old link never works after access comes back on. Stopping the server doesn't wait for requests already running: it stops listening and they finish on their own, so a browser part way through a request can't hold up Settings; restarting on the same port retries the bind for up to a second while the old listener closes. The served `index.html` carries `remote::SERVED_MARK`, so a browser on it with no token, or whose token was refused, shows that the link no longer works instead of the demo. Holding the link is as powerful as using the desktop window, including repository setup commands, so share it only with your own devices.
- The UI uses Astryx 0.6.3 with its neutral theme. Astryx core, theme, CLI, and the StyleX peer are pinned; the compiled theme is imported after the core reset and component CSS. The UI is dark-only, uses local system fonts, and makes no font or asset requests to external hosts.
- Settings, repositories, review loops, and chat load on demand. Pages use Astryx shell, layout, controls, dialogs, chat, and Markdown; only the diff's line grid, the Live page's activity chart, and Bit's picture remain custom (`DiffLines` in `src/Files.tsx`, `ActivityChart` in `src/Live.tsx`, and `src/Bit.tsx` explain why). `src/styles.css` contains viewport framing, system-font tokens, compact chat docking, diff styling, the chart's marks and motion, and Bit's strokes. Bit's classic look is an SVG whose colours are all theme tokens; it animates only while busy. The orb looks are drawn on a canvas by `src/orbs.ts`: each orb is a list of numbers (shape, face, lights, colours in OKLCH) sprung towards its look's targets for the mood, so a new mood, look or colour morphs rather than jumps. Bit's four moods use four of the orbs' six states (happy is idle, busy is working, worried is awaiting input, sleepy is paused). Every orb on screen shares one animation-frame loop that steps the moving ones and draws only those in view; a picture that holds still (the choice lists, note avatars, and everything when the system asks for reduced motion) is posed and drawn once per change. A chosen colour is read from its theme token where the picture sits and turned into the orb's four shades (`tint`); **Its own colours** uses the look's designed palette. Hats stay SVG, in layers over and under the canvas, moved each frame to the head position and tilt that `drawOrb` returns. The Live and Findings pages are derived entirely from the snapshot; they add no backend state. `src/findingIndex.ts` follows each finding by its stable ID (`{reviewId}-{index}`) through later rounds' `priorFindings` to work out its current status, and adds finished scans' findings (IDs `{scanId}:{findingId}`) as open, with no PR. The backend, command allowlist, store behavior, and browser demo adapter are independent of the component layer.
- Astryx component guidance is generated in [`AGENTS.md`](../AGENTS.md). Before changing UI, use `npx astryx component <Name>` for the installed API.

## Design notes

The supplied architecture document was used as a recommendation. This implementation corrects the protocol lifecycle and event names, uses existing installed CLIs instead of bundling a Codex binary, and uses Astryx with its neutral theme.

Not included in this version: code signing for the macOS and Windows installers, and automatic updates. Native prerequisites vary by OS.

## Verification

Controllable app-server fixtures verify model migration, reconnect recovery, immutable queued selections, exact response checks, persistence before inference, and legacy chat pinning without live inference or GitHub publication. A fake `gh` (Unix only) drives the GitHub paths. Component tests cover explicit Settings choices, the legacy selector, Astryx dialog lifecycle and shortcut isolation, guarded composer submission, and Markdown safety (images dropped, links rendered as text, no HTML execution or autolinking). Tests also exercise queue limits, cancellation, publication retry/link rendering, stale file responses, navigation shortcuts, autosave failures/serialization, status/send eligibility, repository validation, worktree cleanup contention/containment/recovery, Markdown export, streamed reports, RPC failures, persistence, and the instance lock. Rust filesystem tests use disposable repositories and state.

Native Linux GTK Save As checks on a virtual display cover successful export, cancellation, overwrite confirmation, and extensionless filename confirmation using disposable review data. Browser checks cover search, review/chat actions, publication previews, changed files, repository configuration, and responsive navigation. Real authentication and model discovery were verified; live inference and posting are not part of the read-only diagnostic (`npm run diagnose`), which uses a temporary state directory.
